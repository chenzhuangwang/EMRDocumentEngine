## 0. 这份文档要解决什么

一次现状盘点得出：引擎相对成熟 EMR 编辑器（以 X-EMR 为参照）缺的不是"小优化"，
而是几块**产品级能力**。其中三块有一个共同特征 —— **引擎已经有料，应用侧零接线**。
这在本仓库是高频陷阱（历史教训：引擎齐备但零接线的"死接缝/孤儿组件"），
评估完成度必须验接线而非验存在。

本文档做三件事：**定序**（先做哪个、为什么）、**定型**（为什么这样设计而不是那样）、
**定边界**（哪些明确不做，记入"不再提"清单）。

## 1. 三个候选、以及为什么是这个顺序

### 1.1 缺口盘点（均有源码证据）

| # | 能力 | 引擎现状 | 断在哪 |
|---|---|---|---|
| 1 | **批量数据绑定** | 只有单点 `Editor.setControlValue(nodeId, value)`（`Editor.ts:1027`）/ `getControlValue`（`Editor.ts:1045`）。**无任何文档级门面** —— 全仓遍历 `pool.nodes` 找 SMART_TEXT 的地方共 7 处，全部只读 | 缺 API |
| 2 | **保存完整性闸门** | 能力齐：`isControlValueComplete`（`document/control/ControlValue.ts:81`，契约 §12.6.2 layer C 已声明）＋ QC 规则 `smarttext_required_not_empty`（`qc/QCEngine.ts:299`）＋ app 侧已在跑 QC（`EditorPage.tsx:460`） | `handleSave`（`EditorPage.tsx:727`）直接 `getSerializedDocument()` 就存（`:734`），**不问必填** |

### 1.2 为什么不能"让应用层自己拼"

这是决定这三个能力**必须落在引擎里**的核心论证，也是本仓库踩过的坑：

- **读方向**：应用层要拿到"文档里全部控件，按阅读顺序"，只能自己遍历。
  但遍历正文的**唯一合法实现**是 `SelectionCollector` 的 W1–W4
  （`bodyParagraphSpine` / `hfParagraphsForExport` / `sectionOf`），
  且 `DocumentWalkGate`（`frontend/src/__tests__/DocumentWalkGate.test.ts`）
  是 CI 硬闸门，禁止闸门外迭代 `doc.body.children`（契约 §31.1）。
  应用层自己写一份 = 第二份遍历 = 与 `collectFields` 三度漂移。
- **写方向**：契约 VR-3 规定运行时值写入**只能**经 `SetControlValueCommand`。
  应用层要批量写，就得自己调 `validateControlValue` + 造命令 + 打包撤销单元，
  等于把 `Editor.setControlValue` 抄一遍 —— 正是"死接缝"的成因。

**结论**：这三件事的正确归属是引擎，且必须**复用既有唯一实现**，不得另起。

### 1.3 排序原则

三条，按优先级：

1. **契约改动面小者先行。** 判据是"要不要动文档格式 / 要不要加节点类型"。
   动格式 = 动 `CURRENT_DOCUMENT_VERSION` + `ModelUpgrader` + 加载校验 + 全部历史文档；
   加节点类型 = 动 `NodeType` + `ContainerChildTypes` + LayoutEngine 三条路径
   + OFD 导出 switch + 命中检测原子类型表（约 6 处字符串比较）+ 格式版本。
   这是 blast radius 最大的两类改动，必须最后做。
2. **外部集成者先受益者先行。** 引擎已经物理剥离、对外分发（契约 §32），
   集成者第一个会问的问题是"HIS 的数据怎么填进病历"。这个问题今天**没有答案** ——
   他们只能拿到 `nodeId` 才敢写值，而 `nodeId` 是运行时生成的、对集成者不可知。
3. **纯增量优于改既有路径。** 新 API 可以既不改既有调用方、又能独立验收；
   改既有路径（如让 `DeleteRangeCommand` 学会留痕）必须连带回归全部编辑操作。

**据此排序：批次一（绑定＋闸门）→ 批次二（计算式）→ 批次三（留痕）。**
批次四条码/二维码、批次五图表另列（见 §5）。

### 2.1 缺口

### 2.2 设计

#### 2.2.1 键策略（本批最核心的设计决策）

X-EMR 按"标识"绑定 —— 设计者给控件起个标识，该标识同时成为 HTML 的 id 和 name。
我们的对应物有三个候选：

| 候选 | 字段 | 优点 | 问题 |
|---|---|---|---|
| nodeId | 节点 id | 唯一 | 运行时生成，集成者不可知；换模板即失效 —— **直接排除** |
| 标识 | `element.code.internal` | 心智模型对齐 X-EMR | 见下方实测 |
| **数据元码** | `element.code.dataElement` | 语义身份、导入器会带进来、引擎已有 `findByDE` 认它 | **同一份病历里可合法重复**（两个"出生日期"，`duplicateElementCodes` 证实） |

**初稿写的是「默认键 = `code.internal`，理由是设计者可控、模板内稳定」—— 实测为假。**
**但第二稿（当天早些时候）的改写也有一处错的**，一并纠正如下。

实测（2026-10-15，逐文件核验）：

- **标识今天在 UI 里不可编辑。** `ControlInputDialog` 的"其他"tab 只有 `prefix`/`suffix`/`tips`/`deletable`/`editable`/`single`（[ControlInputDialog.tsx:355-366](frontend/src/components/dialogs/ControlInputDialog.tsx#L355-L366)）；`DesignControlProperties` 的可编辑字段是 `label`/`tips`/`prefix`/`suffix` + 三个布尔（[:35-46](frontend/src/components/views/DesignControlProperties.tsx#L35-L46)），语义身份区是**纯展示**的 `SemanticRow`（[:70-77](frontend/src/components/views/DesignControlProperties.tsx#L70-L77)，无 `onChange`），面板自己的注释写着"语义身份只读区（契约 §12.5: 只读, 不产生写入）"（[:175](frontend/src/components/views/DesignControlProperties.tsx#L175)）。**结论成立。**
- **⚠ 第二稿此处写错了：「`dataElement` 设计态可编辑」。也是不可编辑的。** 诱因是弹框里那个 label 叫「数据元名称」的输入框（[ControlInputDialog.tsx:251](frontend/src/components/dialogs/ControlInputDialog.tsx#L251)）——它绑的是 `draft.name` → `el.name`（即 `ElementMeta.name`），`code` 一个字节都不碰（`ControlInputDialog.tsx:146-152` 与 `:190-218` 的 result 组装里 `code` 出现 **0** 次）。全仓**没有任何 UI 写入路径** `element.code.*`：19 处 `code: { internal: ... }` 字面量全部是**只读构造** —— 17 处是控件库目录里的**静态常量**（`controlLibrary.ts` 16 条 + `controlConfigShared.tsx:69` 的通用控件种子，即"插入时给的初值"，插入后没有任何回写），2 处在引擎内（`InsertNodesCommand.ts:269` 粘贴时的**兜底默认值**、`lib/export/fields.ts:69` 的**类型声明**）。**没有一处是从输入框回的写。**
- **标识今天也不唯一。** 新建控件走 `initialConfigForCreate` → `controlWidgetById(kind)`，标识是控件库里的**常量**（`CTL_INPUT` / `CTL_SELECT` …，[controlLibrary.ts:124-174](frontend/src/platform/data/controlLibrary.ts#L124-L174)）。同一个 `CTL_INPUT` **可以插入多次** —— 唯一性守卫 `hasSameIdentity` 只对 `definition.single === true` 生效（[InsertControlCommand.ts:137-146](packages/emr-document-engine/src/engine/command/commands/InsertControlCommand.ts#L137-L146)，`elementIdentity` 见 [InsertNodesCommand.ts:52-60](packages/emr-document-engine/src/engine/command/commands/InsertNodesCommand.ts#L52-L60)）。

**所以两个候选今天都不可撰写。** 真实的差别只有三条，且都不是"可编辑"：

1. **导入器会带 `dataElement` 进来**（`dataElement: el.code.dataElement ?? ''`，[TemplateImporter.ts:349-351](packages/emr-document-engine/src/engine/import/TemplateImporter.ts#L349-L351)，夹具里是真实国标码 `DE02.01.001.00`）。**从真实模板导入的文档，`dataElement` 有值；手插的通用控件，两边都是占位常量。**
2. **引擎已有按 `dataElement` 查找的公开 API**（`findByDE`，[ElementFormatter.ts:221](packages/emr-document-engine/src/engine/document/factory/ElementFormatter.ts#L221)，从 [engine/index.ts:135](packages/emr-document-engine/src/engine/index.ts#L135) 导出）；按 `internal` 的 `findByInternal` 也在。两者对等，这条只是"已经有先例"。
3. 通用控件库**自己声明** `DE99.99.00X` 是**合成码**（[controlLibrary.ts:111](frontend/src/platform/data/controlLibrary.ts#L111)："synthetic dataElement DE99.99.00X"）—— 即它**不是**真数据元码，是"通用控件不绑真实编码"的显式标记。这意味着：**手插的一个 `单行文本`，其 `dataElement` 是 `DE99.99.001`；插第二个，还是 `DE99.99.001`。** 通用控件之间必然撞键。

**决定（D1，修正后）**：默认键 = **`element.code.dataElement`，空则回退 `code.internal`**（回退顺序与既有 `elementIdentity` 同口径，不另立一套）。键策略可注入（`keyOf?: (element: ElementMeta | undefined) => string | undefined`，收到的是 element 而非节点）。

理由**不再是**"它可编辑"（两个都不可编辑），而是：

- 从**真实模板导入**（唯一有临床意义的来源）时它**有真值**；
- 语义上它才是"这个字段是什么"的身份，`internal` 更像本地别名；
- 引擎已按它建了查找 API 与导出语义（`findByDE` / CDA 的 `codeSystemName`）。

**同一批内补的是「两个键都可撰写」**，不是只补标识：`ControlInputDialog` 的"其他"tab 增加 `标识` 与 `数据元码` 两个输入框 + 重名提示。这样手插通用控件时用户能给出真正的键，而不是一串 `CTL_INPUT` / `DE99.99.001` 常量。
**⚠ 后来修正：不止这一个弹框。** `ControlChoiceDialog`（单选/复选）也得同样开 —— 契约
§12.5 的「Control Config Dialog」是泛指，两个弹框由同一个右键入口按家族分流。见 §2.6 收尾补充。

**这条改动不需要新命令，现有路径已经支持**（已核对）：
`ControlInputDialog` 的 result 是**整体替换的 `ElementMeta`**（`cloneData(initial.element)` 后改字段），
经 `applyControlConfig` → `UpdateControlElementCommand`（[UpdateControlElementCommand.ts:69-71](packages/emr-document-engine/src/engine/command/commands/UpdateControlElementCommand.ts#L69-L71)）落盘；
"变了没有"的判据 `elementEquals` 走 `stableStringify` 全字段比较
（[:124-145](packages/emr-document-engine/src/engine/command/commands/UpdateControlElementCommand.ts#L124-L145)），
**`code` 在其中**。所以往 draft 里加两个 `code` 字段、在 result 里写上即可，
无需新增命令、无需改引擎。**别被"设计期属性只走 TemplateDefinition"的印象带偏 —— `element` 的写入路径本来就是通的。**

**⚠ 但这触碰一条既有约定**：设计态面板注释与 `DesignControlProperties.test.tsx:68` 的断言（`'DE99.99.004' ... 语义身份只读`）都把"语义身份只读"当成事实。契约里**没有**明文规定它只读（§12.5 通篇未提 `code`），所以这不是违约，而是**契约的空白 + 一条测试锁定的行为**。因此：

- 本批**只开两个配置弹框的写入路径**（`ControlInputDialog` + `ControlChoiceDialog`，见 §2.6 收尾补充），**不动 `DesignControlProperties` 的只读展示**（它的测试继续绿）；
- 契约 §12.5 增补一句明文：语义身份 `element.code` 在**设计态控件配置弹框**中可编辑，在**轻量属性面板**中保持只读展示；
- 那条测试**不改**，它是轻量面板的断言，与本批无关。

**重复键必须显式报告，绝不"后者覆盖前者"**。理由是临床安全：两个"出生日期"字段里静默只填一个，比报错危险得多。返回值里的 `ambiguous` 就是这条。

**必须写进文档的副作用（诚实记录）**：手插的通用控件（`DE99.99.001` 等合成码）**天然互相撞键**。所以"不改标识就直接绑定"这条路，对**通用控件**是不通的 —— 集成者用 `dataElement` 绑定的前提是文档来自真实模板（导入），或实施方手填了码。这不是缺陷，是"通用控件本就不绑真实编码"的必然结果；但它决定了 §2.2.3 的 `ambiguous` 会**经常**被触发，而不是罕见分支。产品上建议：绑定 API 的调用方拿到 `ambiguous` 时应把候选 `nodeId` 列表交给实施方去改标识/码，而不是重试。

#### 2.2.2 读 API（引擎侧）

```
Editor.getBoundValues(opts?): BoundValues
```

返回按**阅读顺序**排列的条目，每条含
`nodeId / key / name / placeholder / value / display / displaySource / filled /
required / readonly / masked / enumOptions`。
顺序必须与导出件的 `order` 逐条一致（跨区域连续：正文 → 页眉 → 页脚）。
**一致性的来源是 §2.2.4 的顺序原语，不是"两份实现碰巧一样"** —— 对拍用例见 §2.4.3。

`key` = 该条目按 `keyOf`（默认 `dataElement` → `internal`）算出的键；
同一 `key` 出现两次时，两条**都照常返回**并在下方 `duplicates` 里点名（读方向不隐藏歧义）。

```
BoundValues = {
  items: BoundItem[]
  /** 出现次数 > 1 的键（读方向也要报，否则调用方以为可以安全回写） */
  duplicates: { key: string; nodeIds: string[] }[]
}
```

#### 2.2.3 写 API（引擎侧）

```
Editor.setBoundValues(obj, opts?): BoundValuesWriteResult
```

行为契约四条：

1. **单一撤销单元。** 整批是一个 undo 步。既有先例：`ReplaceTextCommand`
   把 N 处编辑合成一个撤销条目，内部对每个 smarttext 节点**直接调用**
   `SetControlValueCommand.forward` 而非逐个入栈（[ReplaceTextCommand.ts:217](packages/emr-document-engine/src/engine/command/commands/ReplaceTextCommand.ts#L217)），
   并自带 `_restore` 数组（[:142](packages/emr-document-engine/src/engine/command/commands/ReplaceTextCommand.ts#L142)）。本批沿用同一形状。
   若一个键都没匹配上 → **不产生撤销条目**（空事务不入栈，与 §12.9 的 append 守卫同口径）。
2. **一律经 `validateControlValue`。** 与 `Editor.setControlValue` 同一预校验
   （同源 permissions + dictionary 候选，[Editor.ts:1027-1040](packages/emr-document-engine/src/engine/Editor.ts#L1027-L1040)）。
   VR-10/VR-11 禁止静默四舍五入与截断，VR-9 禁止写候选集之外的值 ——
   **本批不做任何值强制转换**。
3. **部分成功是合法结果，但必须可判定。** 返回
   `{ applied: [...], rejected: [{key, reason}], ambiguous: [{key, candidateNodeIds}], unmatched: [key] }`。
   形状对齐既有 `replaceAll` 的 `{replaced, rejected}` 口径（[Editor.ts:3157-3170](packages/emr-document-engine/src/engine/Editor.ts#L3157-L3170)：
   "replaced 取实际成功节点数, rejected 携带理由 (非静默失败)"）。
   `ambiguous` 的键**一个都不写**（见 §2.2.1 末段：通用控件的合成码让它成为常态）。
4. **不做医疗语义映射。** HIS 传来 `sex:"1"` 而候选集是 `["M","F"]` 时，
   引擎**报 `enum_value_not_allowed` 而不是猜**。转换是平台/适配层的职责 ——
   这既是 §12 的边界（引擎不得硬编码医疗字典），也是 `controlConfigShared`
   与 `dictionaryCatalog` 已经确立的分工。

#### 2.2.4 投影从哪来 —— 初稿方案已被实测推翻（D3）

**初稿写的是**：`Editor` 调不到 `lib/export/fields.ts` 的 `collectFields`（依赖方向
`lib/ → engine/` 单向），所以要把共享内核**下沉**到
`engine/document/control/ControlProjection.ts`，让导出层与绑定 API 都读它。

**前半段成立，后半段被否决：**

- 前半段确认无误。`lib/export/fields.ts:27` 从 `../../engine` 导入；
  `lib/export/index.ts:13` 明确写着"本层**消费** engine, 不被 engine 依赖（§12 特性层）"；
  分包 `exports["./export"]` 与 `exports["."]` 把两者切成两个 bundle。
  所以 `Editor` 里**不能**调 `collectFields`。
- 后半段是高估。全仓 `collectFields` 的**唯一**消费方是
  [EditorPage.tsx:49](frontend/src/pages/EditorPage.tsx#L49) 及其三处调用
  （`:986` / `:1019` / `:1066`，分别是 elements / CDA / OFD 三种导出）。
  **没有任何引擎侧消费者。** 为了给两个新 API 供数而动一份被三种导出共用、
  442 行、`FieldRecord` 有 20 余字段的成熟模块，**风险大于收益**。

**决定（D3）**：本批**不抽取**。绑定 API 的投影**新建于引擎内**，
但必须站在既有的顺序遍历原语之上 —— 那才是这条规则真正的事实源：

```
engine/document/control/ControlProjection.ts   (新, 引擎侧)
  controlProjectionOf(doc, pool, { keyOf?, optionsOf? })
    正文   → bodyParagraphSpine(doc, pool)        ← §31 的唯一合法正文遍历
    页眉   → hfParagraphsForExport(doc, 'header') ← §7.9 变体归属的唯一实现
    页脚   → hfParagraphsForExport(doc, 'footer')
```

**这不是"另写一份遍历"**：`bodyParagraphSpine` 本身就在引擎里
（[SelectionCollector.ts:290](packages/emr-document-engine/src/engine/document/selection/SelectionCollector.ts#L290)），
`hfParagraphsForExport` 也在（[HeaderFooterRegions.ts:139](packages/emr-document-engine/src/engine/document/core/HeaderFooterRegions.ts#L139)），
两者都从 `engine/index.ts` 导出。新模块只做"从段落里挑出 smarttext 子节点 + 组装绑定条目"，
`collectRegion` 今天做的也正是这件事（[fields.ts:375-390](packages/emr-document-engine/src/lib/export/fields.ts#L375-L390)，16 行）。
**重复的是那 16 行胶水，不是遍历口径。**

**关于"两份投影会不会漂移"** —— 诚实记录：会有一点。今天 `display` 的语义在两个口径下
**已经**不同（`fields.ts:211-222` 记录了渲染路径读不到字典候选而导出能读到的刻意差异）。
本批的做法是让绑定投影**与既有数据口径（`getControlSnapshot` / 导出投影）一致**：
inline `format.enums` 优先，字典候选经 `optionsOf` 注入；**渲染路径不动**，它仍然只读
inline `format.enums` —— 屏幕上的字典枚举仍显示机器码。并在返回值里带 `displaySource`
让这一差异可判定。

> **⚠ 这句话初稿写的是「让绑定投影与渲染口径一致」，与本段其余部分自相矛盾**
> （渲染路径恰恰读不到字典候选）。上面的措辞是修正后的。差异本身**保留不动**：
> 对齐渲染是另一件事，契约 §12.10.4 明文禁止夹带进本特性。

**本批实际做的下沉，与"不抽取 collectFields"并不矛盾 —— 判据不同，结论就不同：**

| | `collectFields`（共享内核） | `resolveDisplay` / `enumOptionsFor` |
|---|---|---|
| 是什么 | **遍历**（+ 20 余字段的 `FieldRecord`） | **规则**（值 → 显示文本；候选来源优先级） |
| 下沉代价 | 要把一份 442 行、被三种导出格式共用的成熟模块搬家 | 搬两个纯函数，45 行 |
| 不下沉的代价 | 复制 16 行**胶水**（各side 的遍历口径本就同源） | 复制一条**有语义的规则**，两份必然漂移 |
| 结论（D3 修正后） | **不抽取** —— 但重复的只是胶水 | **下沉** —— 契约 §11「第二次实现即须抽取」 |

所以 D3 的「本批不抽取共享内核」指的是 **`collectFields` 那份内核**，不是"任何东西都不许下沉"。
`resolveDisplay` / `enumOptionsFor` 下沉进 `engine/document/control/ControlDisplay.ts`，
`fields.ts` 改为 re-export（函数体一字未改）—— 方向是 `lib/ → engine/`，§19 允许。

**后续动作（不在本批）**：把"下沉 `collectFields` 本身的共享内核"作为**独立议题**
记入 §5 待议区。等绑定 API 证明稳定、且确实出现第三种消费者时再议 —— 但届时的判据
已经不是"同一段非平凡逻辑被实现第二次"（那条判据对**规则**已经满足并被应用了），
而是"这份遍历是否值得搬家"。两条判据不同，别混为一谈。

#### 2.2.5 完整性闸门

新增窄 API，而不是复用 `runQC()`：

```
Editor.validateRequired(): { ok: boolean; missing: MissingField[] }
  MissingField = { nodeId, paragraphPath, name }   // 形状对齐 QCIssueLocation
```

**为什么不复用 `runQC()`**：`QCResult` 带 `score/grade`（`qc/QCEngine.ts:57-69`），
那是**合规分**；契约 §7.5/§12.6.2 layer E 明确规定合规分与完整性是"不同事实、
不同 owner, 不得合并"。用分数当保存闸门 = 把两个概念混成一个。

**为什么闸门在引擎、但"拦不拦"在应用**：契约 §12.6.2 layer C 已经指定
`isControlValueComplete` "run at save / submit / QC / pre-print" —— 引擎提供判定，
但它**不拥有保存**（保存是 `EditorPage.handleSave`）。
因此设计为：引擎只回答"缺哪些"，应用决定拦不拦。

**产品决策（D2，已拍板）**：`handleSave` 拿到 `!ok` 时
**弹确认框列出未填项 + 可点击跳转，允许继续保存**。不做硬拦 ——
硬拦会在"医生要中途存草稿"时丢工作。
`MissingField.paragraphPath` 就是为了支持跳转（`QCIssueLocation` 已经这么做，
QC 面板的"点击定位"依赖它）。确认框三个出口：跳转到第一条未填项 / 仍然保存 / 取消。

> 「**不动文档格式**（见 3.2.1 —— 这是本设计最关键的一步棋）」，**是错的**。
> 证据两条，都在同一件事上：
> ① 契约 §12.1 明写 `controlType` 引入时「The document format version advances
> from **4.3.x to 4.4.0** with this field's introduction; the migration is a no-op」——
> 而 `controlType` 正是 `TemplateDefinition` 的字段，也正装在**同一个**顶层
> `templateDefinitions` 里；
> ② `ModelUpgrader.ts:14-22` 的版本史是一条一致的规则 ——
> v4.0→4.1「`ElementFormat` **新增可选字段**」、v4.1→4.2「`SmartTextNode` **新增
> 可选字段** value」、v4.3→4.4「`TemplateDefinition` **新增可选字段** controlType」。
> **凡是新增可选字段都升版本**，后三条 NO-OP 也每条都升。当前常量
> `CURRENT_DOCUMENT_VERSION = {4,7,0}`（`DocumentFormatVersion.ts:41`）。
>
> 原文的推理错误在于把「容器字段已存在」当成了「不算格式变更」。可 `controlType`
> 的容器**也正是** `templateDefinitions`，它照样升了版本。见 §3.2.1 的改写与
> §3.5 的核验记录。

### 3.1 缺口

X-EMR 提供四件东西：赋值式 `= id1 + id2`；触发式 `if(sex==0) SHOW(#id1) else HIDE(#id1)`；
内置 `GETAGE()/DIFF_DATE_HOURS()`；注册接口 `editor.calculate.registerFunction(name, fn)`。
我们一件都没有。这不是锦上添花 —— "性别=男则隐藏孕产史"、"年龄由出生日期算"
是病历刚需。

**必须避开的坑**：X-EMR 直接跑 JS 语法（等于 eval）。我们**必须**走白名单表达式求值器。

### 3.2 设计

#### 3.2.1 公式住在哪 —— 决定了本批的整个成本

| 方案 | 代价 |
|---|---|
| 新节点类型 `computed` | `NodeType` ＋ `ContainerChildTypes` ＋ LayoutEngine 三条路径 ＋ OFD switch ＋ 命中检测原子表 ＋ **格式版本 4.7.0→4.8.0** |
| 新字段落在 `ElementFormat` | 契约 §12.6.2 layer D 明确是"无值语义的表现/查找/高级语义"，而公式**是值语义** → 归类错误 |
| **落在 `TemplateDefinition.formula?: string`** | **五笔面成本全免**（NodeType / ContainerChildTypes / 三条布局路径 / OFD switch / 命中原子表）；**但仍要升格式版本 4.7.0→4.8.0 + 一条 NO-OP 迁移** |

**决定：`TemplateDefinition.formula?: string`。**（版本那一笔不再是区分项，见下方修正。）

论证：
1. 契约 §12.1 定义 `TemplateDefinition` 为"模板**作者**在设计期如何配置该控件"
   （`deletable/editable/tips/label/prefix/suffix/single/controlType`）。公式由模板作者撰写，
   语义完全吻合。
2. ~~`templateDefinitions` 已经作为**顶层字段**随文档序列化……→ **不动格式版本，不动 `ModelUpgrader`**。~~
   **⚠ 此条 2026-10-16 已被推翻（详见本节开头的核验说明）**：容器字段已存在**不等于**不算
   格式变更 —— `controlType` 当年装的就是同一个 `templateDefinitions`，照样把版本从
   4.3.x 推到 4.4.0。仓库的规则是**看字段的引入**，不是看容器。
   **该条改写为**：`templateDefinitions` 已经在序列化/加载两侧配对得手
   （`Serializer.ts:124` / `DocumentLoader.ts:407`），所以**新字段不需要任何数据搬运**
   —— 迁移是一条**显式 NO-OP**（照 4.4→4.5 / 4.5→4.6 / 4.6→4.7 三例的形状：
   `breaking: false`，upgrade 原样返回）。省掉的是**改写与回填**，不是版本号本身。
3. `Draw` 已在构造时把 `TemplateDefinition` 通过 `controlInfoOf` 注入 LayoutEngine
   （`Draw.ts:169-178`，读 `def?.controlType` 等）→ 布局层**已经有拿到公式的缝**。

**决定余量的诚实修正**：原稿把「零格式变更」当成选择 `TemplateDefinition` 的**首要理由**，
现在这一笔省不掉了。决定本身仍成立，但理由是**那五笔面成本**（新节点类型要动 `NodeType`、
`ContainerChildTypes`、三条布局路径、OFD switch、命中原子表），**不是**"格式不动"。
5 比 1 的账仍然清楚，但要按 5 比 1 讲，不能按 5 比 0 讲。

**连带影响（必须一起改，否则文档自相矛盾）**：
- 批次三的格式版本**顺延为 4.8.0 → 4.9.0**（§4 前言原写"4.7.0 → 4.8.0"，且把
  "**动文档格式**"当成它与批次二的**区别**——该区别已不存在）。
- 批次三"放最后"的理由**仍然成立**，但要换成真理由：它的 blast radius 大在
  **`NodeType` 相邻面 + `TextNode` 加字段 + 修订 §7.3/§12.2**，而不是"只有它动格式"。
- §14（契约）要**记两条**新的显式 NO-OP 步骤，不是一条。
- `ModelUpgrader.test.ts` 要加一条：4.7.0 文档升到 4.8.0 后**逐字节等价**（NO-OP 的判据）。

**代价（诚实记录）**：公式不随导出件传递（`templateDefinitions` 是 per-editor store，
不是文档内容）。因此**计算结果是易失的派生值**，见 3.2.3。

#### 3.2.2 求值器（绝不用 eval）

新建 `engine/evaluation/ExpressionEngine.ts` —— 归属 `evaluation/` 而不是 Editor.ts，
既符合 §11（"先判断哪个子系统拥有它，不要自动往 Editor.ts 加代码"），
也符合该目录已有的定位（`ControlScorer.ts` 头注："只读派生语义"）。

- **词法 + Pratt 解析 + 树遍历求值**。语法子集：
  引用 `[internal]` / 裸标识符、数字/字符串字面量、
  `+ - * / %`、`== != < <= > >=`、`&& || !`、括号、
  三元 `IF(c, a, b)`、内置函数表、`SHOW(#id)` / `HIDE(#id)`。
- **纯净性（§27–§29）**：求值器不触任何宿主全局。**时间/日期事实经 context 注入** ——
  与 `FieldFormatter.resolveFieldText` 的 `FieldTextContext`（`document/factory/FieldFormatter.ts:27-40`）
  完全同构。这是本仓库已经验证过的形状：一个 document 域的纯函数 + 调用方填充的上下文对象
  + 两个消费者（布局量宽 / 渲染取值）。
- **内置函数**：`GETAGE`（出生日期→年龄，含月龄）、`DIFF_DATE_HOURS`、`DIFF_DATE_DAYS`、
  `SUM`、`ROUND`。全部走注入的时间基准。
- **自定义函数**：`Editor.registerCalcFunction(name, fn)`。信任级别等同插件
  （集成者自己的代码，不是终端用户数据）。文档必须写明：
  **求值器不触宿主全局，只有已注册的纯函数可被调用**。

#### 3.2.3 派生值不落盘

**决定：计算结果不写入 `SmartTextNode.value`，只在读取路径上注入。**

三条理由：
1. VR-1 规定 `value` 是"规范运行时值"。若引擎把算出来的值写进去，同一字段就有两个事实源。
2. 每次重算都是文档变更 → 撤销栈塞满派生值的变更，用户按 Ctrl+Z 会看到"什么都没变"的一步。
3. **临床安全**：`required` 校验若把"算出来的值"算作已填，会让医生从未看过的字段通过闸门。

因此计算式字段在语义上是**派生字段**，与域代码（`FieldNode`）同类 ——
域代码今天的做法就是答案：`Draw.resolveFieldText` 每帧重算，从不落盘
（`Draw.ts:1804-1815`，契约 §4 "field resolution MUST have exactly one implementation"）。

#### 3.2.4 布局与渲染怎么接（不改 §12.8 的唯一实现）

- **量宽**：`smarttextLayoutHint` 是全仓**唯一**决定控件盒宽与折行的实现
  （`layout/control/ControlLayoutHint.ts:62-147`），契约 §12.8 明令渲染侧
  "MUST NOT re-derive the wrap"。计算值必须在**布局之前**解出来并作为
  `display` 传进 `smarttextLayoutHint`（`LayoutEngine.ts:306-329` 已经在传 `display`）。
- **取值**：渲染侧照 `Draw.resolveFieldText` 的样子，在 dispatch 处
  spread 克隆注入（`Draw.ts:1257`、`:1323` 是既有两处），
  **不把派生值写进 SLIF**，与域代码同口径。
- **可见性（SHOW/HIDE）**：扩展已经存在的注入缝
  `LayoutEngine.setControlInfoOf`（`LayoutEngine.ts:1408`，`Draw.ts:169` 注入）——
  加一个 `visible: boolean`。**LayoutEngine 不需要知道"公式"是什么**，
  它只问"这个控件可见吗"。这是耦合最小的设计，且保持 §12.8 不变。
- **依赖图与失效**：公式 X 引用 A、B 时，A/B 变化必须让 X 重算。
  必须在 `setDocument` / `setControlDefinition` 时建**依赖索引**，并在
  `SetControlValueCommand` 完成后按索引入队重算。
  可用信号已有：`NodePool.updateNode` 会 bump 每节点版本号
  （`document/core/NodePool.ts:220-229`，`getNodeVersion` 已被增量布局缓存使用）。
  **环检测必须在建图时做**（`= id1 + (id1*2)` 之类），报错而非死循环。
- **computed-value set 归谁、怎么给到 Draw**（核验后补的一条）：
  它是**派生状态**，随文档走，故由 `Editor` 持有（如 `evaluation/` 下的一个实例），
  并沿**既有注入缝**交给渲染层 —— `Draw.setDocument(doc, pool, presentationStyles,
  templateDefinitions)`（`Draw.ts` 构造后由 Editor 调用）再加一个参数即可。
  **不新开缝**：Draw 已经在同一处拿 `templateDefinitions`，而公式就住在那里，
  两者不同时给到才会需要额外的查找路径。
  布局量宽、渲染取值、导出（§12.12.8 / §3.4 第 4 条要求三处一致）都读**这一份**，
  不各自求值。
- **两遍布局**：`fullLayout` 已经是两遍（`LayoutEngine.ts:129-147`，第二遍用真实页数）。
  计算值若依赖页码，走同一机制。

#### 3.2.5 已知边界（必须写进文档，不能留给下一个人踩）

- 隐藏控件跨越选区/光标：隐藏控件不产出 SLIFItem → 自然不可命中、光标进不去。
  但**跨隐藏控件的字符偏移计数**需要核对 `paragraphTextLength`
  （`document/selection/SelectionCollector.ts:63-75`：文本节点按 `text.length`，
  原子内联按 1）。这是本批最容易出的静默错位。
- 公式只存在于 `templateDefinitions`：文档被剥离模板元数据后，值留在最后一次
  已算出的状态（若曾落盘）或退化为占位符（不落盘时）。**必须选后者并说明**。

#### 3.2.6 开工前核验后新增的定论（§3.5 翻出来的 4 条）

原稿没写这四条，都是回测代码时才显形的。**都不是"顺手加"，是不写就会各自出错的**。

**（1）引用撞键：报歧义，不求值，绝不挑一个。**
公式用 `[键]` 引用别的控件，而那个键就是 §12.10.1 的**绑定键** —— 于是 §12.10.2 的
"一键多节点是常态"在这里同样成立（手插通用控件撞合成码）。原稿只说了语法，没说撞键怎么办。
**照批次一已裁定的同一条立场办**：一条引用命中 ≥2 个控件 → **该条引用判为歧义**，
公式**整体求值失败**并回报候选 `nodeId` 列表，而不是"取阅读顺序第一个"。理由与 §12.10.2
一字不差：静默挑一个出来的值，"看着算了、实则算错"，是临床安全问题。
（这也让"公式引用"复用了 `setBoundValues` 的同一份键解析与同一条歧义口径。）

**（2）类型与强制转换：数字串参与算术时数值化，非数字串报错。**
`ControlValue` 是 `string | number | string[]`，而 `[N1] + [N2]` 需要数字。
规则：算术/比较运算数若为**可完整解析为有限数字的字符串**（`Number(s)` 且
`Number.isFinite`）→ 按数字参与；**否则报错**（不静默变 `NaN`、不把 `NaN` 当假值继续算）。
这是**读路径**的宽松，与 §12.10.3「写入不做任何强制转换」**不冲突** —— 那条管的是把外部值
写进文档，这里管的是把文档里的值拿去算；两者不得互相引用为"先例"。
`string[]` 参与算术 = 报错（除 `SUM()` 这类显式接受多值的函数）。

**（3）计算值**不算**"已填"，§12.11 闸门必须看不见它。**
原稿 §3.2.3 的理由 3 提过，但没进契约修订清单。明文：`isControlValueComplete` 只看
`SmartTextNode.value`；派生值不写入 `value`，因此**必填项不会因为"算出来有个值"而通过闸门**。
理由是临床安全：医生扫一眼没填、其实被算出来了的字段，与被算错的字段，是同一种事故。

**（4）时间基准在"重算"时读一次，**不是**按趟读。**
见 §3.5 第 15 条。**这里纠正了本节初稿的一处自相矛盾**：初稿写"按趟快照一次
（布局趟 / 绘制趟 / 导出趟各自取一次）"，而它给的理由是"防布局按 40 岁算宽、绘制按
41 岁画字"—— **按趟快照恰恰防不住这个**：`render()` **不重排**（`Draw.ts:568` 起，
它画的是上一次布局产出的 `this.pages`），而滚动/缩放每次都跑 render。布局在 23:59:59、
绘制在 00:00:01 就会分叉，且天天会。故正确机制是：

- 引擎维护**一份 computed-value set**（控件 → 解析出的 display + visible，或一个错误），
  **按文档状态 memo**；依赖变化才重算（§12.12.6 的依赖索引就是它的失效依据）。
- **时钟在重算那一刻读一次**，同一次重算里所有求值共用它；`evaluation/` 内不得读钟。
- 于是布局 / 渲染 / 导出**读的是同一份**（构造上一致），§3.4 第 4 条的往返一致性才**可能**成立。
- **代价要说明白**：时间相关值**在文档闲置时不会自己走**（`GETAGE` 算出的年龄要等依赖变化
  或换文档才更新）。这对病历是**想要的**行为——医生读到的值不该在他签字前悄悄变。
  定时刷新或打开时刷新是**宿主**的事，不在本节。

### 3.4 验证

1. **闸门（静态源码扫描）**：`evaluation/` 下不得出现 `eval(`、`new Function`、
   `globalThis`、`window`、`new Date()`（时间必须注入）。形状同 `I18nGate` / `DocumentWalkGate`。
2. **闸门**：禁止在 `render/` 或 `layout/` 内重新实现折行 —— 断言控件折行只出现在
   `ControlLayoutHint`（§12.8 的机器守卫；今天没有这条闸门，本批补上）。
3. 用例：词法器/解析器/求值器各层；环检测；未注册函数报错；
   `SHOW/HIDE` 影响布局产出；`GETAGE` 边界（闰年、当月、未填出生日期）；
   依赖失效（改 A → X 重排）。
4. 往返一致性：同一文档在屏幕渲染与打印/导出件里计算值相同
   （契约 §4 的硬要求，`preparePrintPages` 走同一条 dispatch）。
5. **NO-OP 迁移**：4.7.0 文档升到 4.8.0 后**逐字节等价**（形状照
   `ModelUpgrader.test.ts` 里既有三条 NO-OP 的判据）。
6. **§3.2.6 新增的四条各要一条会红的用例**：
   - 引用撞键（同键两个控件）→ 报歧义、**整个公式不求值**、回报候选 `nodeId`；
   - 类型：`'3' + '4'` 得 `7`（数字串数值化）；`'abc' + 1` **报错**而不是 `NaN`；
     `string[]` 参与算术报错；
   - **闸门交集**：一个带公式的必填控件，公式算得出值但 `value` 为空 →
     `Editor.validateRequired()` 仍报它缺（这条同时锁住 §12.11 与 §12.12 的边界）；
   - **时钟按重算读**：同一份 memo 下，布局与渲染读到的计算值**必须相同**
     （判据：注入一个固定时钟 → 布局一次、渲染一次，两者取到的年龄一致；
     再改一个依赖 → 重算，值随之更新）。真挂钟不可用（闸门 1 已禁 `evaluation/` 读钟）。

**第 14 条为什么是错的**（两条独立证据，都指向同一条规则）：

- 契约 §12.1 关于 `controlType` 的原文：*"The document format version advances from
  **4.3.x to 4.4.0** with this field's introduction; the migration is a no-op (no data
  rewrite), leaving pre-4.4 entries without controlType."* —— `controlType` 是
  `TemplateDefinition` 的字段，装的就是**同一个**顶层 `templateDefinitions`。
- `ModelUpgrader.ts:14-22` 的版本史是一条**一致的规则**：
  `v4.0→4.1 ElementFormat 新增可选字段`、`v4.1→4.2 SmartTextNode 新增可选字段 value`、
  `v4.3→4.4 TemplateDefinition 新增可选字段 controlType`。
  **凡是新增可选字段都升版本**；后面三条显式 NO-OP 也每条都升，没有例外。

原文的推理错在把「容器字段已存在」当成了「不算格式变更」。可 `controlType` 的容器
**也正是** `templateDefinitions`，它照样升了版本。所以规则看的是**字段的引入**，
不是容器。当前 `CURRENT_DOCUMENT_VERSION = {4,7,0}`（`DocumentFormatVersion.ts:41`）
→ 批次二升到 4.8.0，批次三顺延到 4.9.0。

**结论未变、余量变小**：`TemplateDefinition.formula` 仍是正确选择（省掉 `NodeType`、
`ContainerChildTypes`、三条布局路径、OFD switch、命中原子表五笔面成本），但**省不掉版本这一笔**。
按 5 比 1 讲，不按 5 比 0 讲。

**第 15 条（回测时新发现，设计未覆盖）：时间基准今天**没有**注入缝。**

§3.2.2 写的是"时间/日期事实经 context 注入 —— 与 `FieldTextContext` 完全同构"。
**形状确实同构，注入位置不是**：全仓唯一的域代码消费者 `Draw.resolveFieldText`
（`Draw.ts:1806`）自己写死 `now: new Date()`（`:1811`）—— **渲染层现读挂钟**，
上面没有任何一层注入它。而它在**逐项**渲染循环里被调用（`:1257` / `:1323`）。

两笔后果：

1. **跨趟不一致**：计算值若照抄这个形状，布局趟与绘制趟各读一次挂钟 —— 跨过分钟/日界
   （`GETAGE` 的经典边界）就会得到两个值。控件盒宽按 A 算、绘制文字按 B 画，正是 §12.8
   存在的意义所要防的那种静默错位。
2. **§3.4 第 4 条（屏幕与打印/导出的计算值相同）直接受威胁** —— 那条要求本来就假定
   "同一条 dispatch"，而钟在那里会走。

**故本批新增一条硬约束**（见 §3.2.6(4)，那里记了这条的二次修正）：
**时钟在"重算 computed-value set"那一刻读一次**，该 set 按文档状态 memo、依赖变化才重算；
**不得逐项 `new Date()`，也不是"按趟快照"** —— 后者防不住第 1 笔，因为 `render()` 不重排。
既有域代码的逐项读法是**已有偏差**，本批**不顺手改它**（不在范围），但要在 §12.12 里
把公式的要求写清，并登记这条差异 —— 否则下一个人会把域代码的写法照抄过来。

### 3.6 应用侧作者化面（2026-10-16 裁定：**本批包含**）

原稿通篇只有引擎侧：求值器、布局接线、依赖图、可见性 —— **没有一句话说公式在哪写**。
这是必须补的，而且**不能照批次一的先例推**：批次一的绑定 API 消费者是**外部集成方**
（HIS/EMR 平台），所以引擎-only 交付是完整交付；公式的消费者**就是本应用的模板作者**，
没有撰写面交出去的东西在本仓**没人能用**（正是 [[engine-complete-wiring-missing]] 那个陷阱）。

三件事：

**（1）公式在哪写 —— 两个配置弹框都开，共用同一个组件。**
新增一个「计算」tab 到 `ControlInputDialog` 与 `ControlChoiceDialog`，两边渲染同一个
`FormulaField`（放 `controlConfigShared`，照批次一 `SemanticIdentityFields` 的做法）。
**两条都开是硬要求，不是顺手**：批次一刚吃过"同一条契约条款只兑现一半控件"的亏
（语义身份只给了输入域弹框，单选/复选绑不上），这次一个条款要从两个弹框同时进。
不塞进已有的「其他 / 基础属性」tab：那个 tab 已经装了语义身份 + 前后缀 + 三个标志，
再塞语法帮助与实时错误就成了三件事的垃圾桶。

**（2）引用的键就是绑定键 —— 帮助文案必须说清，且撞键时按 §3.2.6(1) 回报。**
公式里写 `[键]`，那个键就是 §12.10.1 的绑定键（数据元码优先、空回退标识）。
所以「公式」tab 要**列出当前文档里可引用的键**（直接从 `Editor.getBoundValues()`
去重拿），并把撞键的键标出来（它们会报歧义）。**复用同一份投影**，不另建一份键清单 ——
两份清单必然漂移，而且会漂移成"UI 说能引用、求值说歧义"这种最难查的形态。

**（3）语法/求值错误回报作者，且**不阻断**应用。**
与批次一的撞键提示同一姿势：实时校验、行内提示、`onApply` 不被拦。
理由也一样 —— 作者可能正写到一半；硬拦会把"存草稿"变成不可能。
错误分类要**可判定**（引用未找到 / 撞键歧义 / 语法错误 / 未注册函数 / 环），
不是一句"公式有误"。

**时间基准谁注入：宿主不需要新增接线。** 按 §3.2.6(4)，时钟在**重算那一刻**读一次
（由持有集合的 `Editor` 读），各趟只在开头 `ensure()` 一次 —— 不脏则连钟都不读。
宿主无感。只有在**将来**要支持"预览指定时刻"时，才需要给宿主一个注入缝；那时再加。

### 4.2 设计

#### 4.2.1 模型：挂在文本节点上，不挂在范围上

**决定**：`TextNode.revision?: RevisionMark`（不是范围）。

```
interface RevisionMark {
  type: 'insert' | 'delete' | 'modify'
  author?: string
  authorId?: string
  at?: number
  /** type==='delete' 时保留被删原文（Word 模型：删掉的文字留下并标记） */
  original?: string
}
```

**为什么不学批注的"范围"模型**：批注是**旁注**（不改变内容），所以用
`DocumentTree.comments` 顶层集合 + `{path, offset}` 范围 + Draw 里逐帧重算几何
（`Draw.ts:263-311`，屏幕 `:610` / 打印 `:1943` 共用）—— 那套对批注是对的。
但留痕是**内容属性**（这段文字是新插入的），它必须跟着文字走：
复制、删段、合并段、分页都要跟着。挂在节点上天然获得这一切；
挂范围则每次编辑都要重锚（而 `CommentThread.anchorStatus` 字段声明了
`'valid'|'reanchored'|'degraded'`，实测**从未被任何代码更新**
（只在校验时硬编码 `'valid'`，`Editor.ts:2280`）—— 重锚未实现，不要重蹈）。

**为什么不放在 `TextStyle` 里**：`TextNode extends BaseNode, TextStyle`。
放进 `TextStyle` 会让格式刷（`FormatPainter`）把留痕一起复制 —— 那是错的。

#### 4.2.2 打通 SLIF 与渲染（4 处小改，把半成品接上）

1. `SLIF.ts`：`SLIFItem` 加 `revision?: {type: string}`。
2. LayoutEngine 三处 push 点从 `el` 透传（`LayoutEngine.ts:522-539` 正文 /
   `:953-967` 单元格 / `:1308-1322` 页眉页脚）—— **同一文件里 `underlineStyle`/`highlight`
   已经这么透了**，照抄即可。
3. `ParticleAdapters.ts:32-46` 把 `revision` 传给 `TextParticle.render`。
4. `delete` 类型**同时**画出删除线（Word 的删除线语义；`TextParticle`
   已支持 `strikeout`，无需新代码）。删除线在**渲染侧**由 `revision.type`
   派生（`ParticleAdapters` 里 `strikeout: item.strikeout || rev?.type === 'delete'`），
   不写进 SLIF 的 `strikeout` —— 否则 `showRevisionMarks=false` 关不掉它
   （视图开关只能改绘制，不能改 SLIF/文档）。

#### 4.2.3 视图开关，不重定义 `clean` 模式

**决定**：加运行时视图开关 `showRevisionMarks: boolean`（默认 true），
**不**把 `EditorMode.clean` 改成"留痕模式"。

理由：`clean` 今天是 **readonly + i18n 标为"纯文本"**
（`KeyboardHandler.ts:54` 把 `clean` 与 `readonly`/`print` 并列成只读；
`i18n/index.ts:573` 的 `mode.clean` 文案）。改它的语义是契约级语义迁移，
且会与"只读"这一既有含义打架。

**既有形状直接对齐**：`showInvisible` 就是这件事的先例 ——
`Editor.setShowInvisible/getShowInvisible`（`Editor.ts:3115-3119`）＋
`Draw.showInvisible` ＋ `RenderOptions.showInvisible`。照抄该形状，
新增 `setShowRevisionMarks/getShowRevisionMarks`。
（把 `clean` 模式绑到这个开关上是**另一件事**，如要做，单独提出并单独改契约。）

#### 4.2.4 谁产生留痕 —— 单一盖戳点

需要一个运行时开关（Word 的"修订"）：`Editor.setTrackChanges(on)` +
当前用户 `Editor.setCurrentUser({name, id, level})`（PRD F21.6"修订者颜色"需要）。

**关键设计：盖戳在命令层唯一一处，不在每个命令里各写一遍。**

`CommandManager.buildContext()` 已经在向命令注入事实
（`command/CommandManager.ts:75` 注入 `getDictionaries()`）。照此加一项
`getRevisionContext()`，返回 `{tracking, user, at}` —— **`at` 每执行一次命令
只读一次时钟**（`at` 在 buildContext 里取一次，不在各命令里各取）。

会改动**文本内容**的三个命令调同一个共享助手 `stampRevision(node, ctx)`：
`InsertTextCommand` / `DeleteRangeCommand` / `ReplaceTextCommand`。

`SplitParagraphCommand` / `MergeParagraphCommand` **不在其列**（开工前核验修正）：
本模型没有段落标记节点（段落只是 children 数组，`ParaNode` 不承载文本），
回车/合并不产生任何可挂标记的对象。它们只**保留**既有标记，不产生新标记。
（原方案把这两个也列进来，是把 Word 的"段落标记也可被修订"直接搬了过来 ——
那个模型里有 `¶` 这个字符，这里没有。）

撤销：留痕挂在节点上，而这些命令**本来就**用子树快照做 invert
（`captureSubtree` / `ParagraphSnapshot` / `MintingOnce` 等），invert 时节点连同
`revision` 一起还原 —— 大部分场景**免费**。需要逐一核对而非假定。

**盖戳必须可重放**（契约 §8.3 的推论）：命令首次 forward 时缓存标记，
重放时复用。否则 `at` 每次都是新时钟，`undo×N → redo×N` 的字节级判据当场破。

**删除待插入内容 = 取消**：带 `insert` 标记的文字被删时不叠加 `delete` 标记，
而是直接移除 —— 一次没被接受的插入被撤销，不该变成一条删除记录。

**非文本节点不可挂标记**：`image` / `smarttext` 的删除是结构性的，**不追踪**。
这是显式边界（标记只住在 TextNode 上），不是遗漏。

#### 4.2.5 接受/拒绝

`acceptAll` / `rejectAll` / 逐处接受（X-EMR 有前两者；PRD F14.2 要"逐处接受/拒绝"）。

- `insert` 接受 → 去掉标记（文字留下）；
- `insert` 拒绝 → 删除该节点；
- `delete` 接受 → 真正删除节点；
- `delete` 拒绝 → 去掉标记（文字留下，恢复原状）。

必须是命令（可撤销）。`DocumentDiffer` 已有的 `'insert'|'delete'|'modify'|'equal'`
（`engine/DocumentDiffer.ts:20`）**不是**留痕模型 —— 它是两版本文档的差异，
不持久化，不要混用（`DocumentCompareView` 是并排比较视图，另一件事）。

#### 4.2.6 导入器：从"丢弃"改成"导入"

按开工前核验修正后的口径（见 §4.1 的核验框）：

1. **主路径（真实线上格式）**：每个行内节点先读自身 `rtype`，把它转成
   `RevisionMark` 挂到产出的 TextNode 上。`text` 与 `checkfield` 都映射成
   TextNode，因此两者都天然保留标记（真实样本里正是这两类宿主）。
   `date`（`'YYYY-MM-DD HH:mm:ss'`）解析为 epoch ms；解析失败则只丢 `at`、
   保留 author。
2. **夹具形态（独立 `insert`/`delete` 标记节点）**：标记本身无内容，作用于
   后续行内兄弟，直到下一个标记或段落结束。块级独立标记没有已验证的范围语义，
   保持跳过并在契约里登记为显式边界 —— **不能**声称"两处都已导入"。
3. `TemplateImporter.test.ts:270` 那条"锁死丢弃"的用例必须改，并新增一条断言
   `rtype` 被导入（含 author / authorId / at）。

| 格式版本升级影响历史文档 | 三 | 显式 NO-OP 迁移（§14 既有惯例：仅加可选字段，不重写不回填） |
| 接受/拒绝后撤销不还原标记 | 三 | 逐命令核对 invert；以"带 id 序列化逐字节相同"为判据 |

## 8. 验收口径

每批独立验收，共同门槛：

1. `cd frontend && npx vitest run` —— 全量绿（含引擎包用例）。
2. `cd frontend && npx tsc --noEmit` —— 干净。
3. `cd frontend && npm run build` —— 通过。
4. 新增的静态闸门本身有"闸门自身没读空"的用例
   （教训：CSS/源码读不到时断言会假绿，比没有闸门更危险）。
5. i18n：所有新增 UI 文案走 `I18nGate` 覆盖的键，zh-CN/en-US 双份
   （教训：i18n"全量替换"曾是假结论，须以闸门为准）。
6. 真实浏览器复核（`bsk`）：关键交互在真应用里跑一遍，不只看单测。
7. AOCI：受管对象变化后 `aoci_maintain` → 撰写条目 → `update_entry` →
   `verify`/`check`/`guide` 三闸门 aligned（`code:` 规范身份；字段先按 token 配额自查）。
8. 每批一个提交，提交信息写清"为什么"。
