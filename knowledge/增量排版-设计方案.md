# 增量排版立项设计（2026-10-19）

> **状态**：M1、M2a 已完成（2026-10-19），M2b 未开工
> **前置事实**：契约 §16.1「INCREMENTAL LAYOUT STATUS」、功能清单 #100-#104
> **一句话**：当前每次 `document:changed` 都是全量排版；本文定义怎样把「段落级缓存 + 从首个脏页重分页」做成可验证、可回滚的增量管线。
>
> **M1 落地物**：`IncrementalLayout.paragraphKey(pool, paraId)`（键 = 段落身份 + `structureVersion` + 段落版本 + 逐子节点 id@版本）；`ParagraphLayoutKey.test.ts` 9 例（含「兄弟段落改动不污染本段键」）；`IncrementalLayoutEquivalence.test.ts` 4 例（比较器元测试、确定性基线、40 步随机编辑、含页眉场景）。M2 只需把等价性断言的一侧换成增量引擎，用例体不变。
>
> **M2a 落地物**：`LayoutEngine` 内置段落行缓存（按段落 ID 存最新一份），只缓存**纯文本、非列表**段落；键 = `paragraphKey` + 可用宽 + 修订显隐。`ParagraphLineCache.test.ts` 9 例锁正确性与命中率；等价性文件新增「持久引擎 vs 全新引擎 40 步」硬门。分页仍是全量（M2b）。

| 事实 | 位置 |
|---|---|

| `DirtyTracker` 采集了脏标记，`document:changed` 也发了 `dirtyNodeIds`，但无消费方 | [CommandManager.ts](../packages/emr-document-engine/src/engine/command/CommandManager.ts) L159-171 |

**结论**：这四件不能「接上线就生效」。接上 `incrementalLayout()` 只是把同一份全量结果里的前几页对象复用，计算量不变；要省计算必须重写段落级缓存管线。故立此文档，不在代码里留「看起来增量」的假象。

## 2. 目标与非目标

### 目标

1. 单字符编辑的成本从 `O(全文字段落)` 降到 `O(脏段落 + 受影响页)`。
2. **正确性判据**：任意编辑序列之后，增量结果与全量结果**逐字节相同**（SLIF 深度序列化比较，含 pageIndex/items/几何）。
3. 失效规则可枚举、可测试；宁保守，不猜。
4. 开关可关闭：`Draw.recomputeLayout` 能退回全量，用于对比与线上回滚。

### 非目标

- 不改渲染层与粒子管线。
- 不做内存淘汰策略（`MemoryManager` 另议）。
- 不做后台排版/Worker（后续可单独立项）。
- 不改变 SLIF 数据结构与导出结果。

## 3. 设计

### 3.1 布局单元与缓存键

段落是唯一布局单元。一个段落的排版结果 = `ILine[]` + 总高 + 列表编号上下文。

缓存键必须覆盖「段落自身内容 + 子节点内容 + 结构位置」：

```
key(paraId) = hash(
  pool.structureVersion,          // 任何 children 增删/移动
  pool.getNodeVersion(paraId),    // 段落样式变化
  for child in para.children:     // 文本/控件/域/图片等
    child.id + pool.getNodeVersion(child)
)
```

- `NodePool` 的版本号只在**被更新节点自身**上自增（L220-228），不会向父节点冒泡 —— 所以必须聚合子节点版本，不能只读段落版本。
- `structureVersion` 是全局计数（任何结构变更都变），用它做保守失效：结构编辑会让全部段落缓存失效，但结构编辑远少于打字。
- 缓存值只存**段落内**结果（行元素、行高），不存页码 —— 页码由分页阶段重新推导。

### 3.2 失效规则

| 变化 | 失效范围 | 理由 |
|---|---|---|
| `InsertText` / `DeleteRange`（段内） | 该段落 + 其后分页 | 影响行数与总高 |
| `SplitParagraph` / `MergeParagraph` | 两段 + 其后分页 | 结构变化 |
| `ParagraphStyleCommand` | 该段落 + 其后分页 | 缩进/行距/列表改变行宽与行高 |
| `FormatTextRangeCommand` | 该段落 + 其后分页 | 字号/字体改变行高 |
| 表格内编辑 | 该 cell 所属表格块 + 其后分页 | 表格分页以块为单位 |
| 页眉页脚/页边距/纸张 | **全量** | 版心与页高改变，所有行宽失效 |
| 域代码 `PAGE` / `NUMPAGES` | **全量** | 总页数变化会改预留宽（`FieldReserveContext.totalPagesHint`） |
| 脚注增删 | **全量** | 脚注区占用页底高度，且编号全局连续 |
| 列表编号 | 该列表后续同列表段落 | 编号是跨段落状态 |
| 计算值/时钟变化 | **全量**（或按脏键） | `ComputedValues` 每趟 ensure，键变化会影响显示串宽度 |
| `invalidation === 'none'` | 跳过排版 | 契约承诺无 reflow；先加断言测试再启用 |

无法证明安全的场景一律升级为全量 —— 这比错排更容易发现和回滚。

### 3.3 分页重算

1. 用缓存重建段落 → `ILine[]` 流（只重算脏段落）。
2. 找到**首个受影响页**：`PageStartTable` 记录「页 → 起始段落」，取所有脏段落中的最小页。
3. 从该页起始段落重新跑 `PageBreaker`，保留之前页面的 SLIF 对象。
4. 页码变化若影响域代码预留宽（`representativeFieldText`），触发一次全量修正 —— 与现有 `fullLayout` 的两轮策略一致。

### 3.4 接线点

M2a 已落地「段落级缓存」这一段（`LayoutEngine` 内部，对调用方透明）：

```
Draw.recomputeLayout
  → LayoutEngine.fullLayout
      ├─ 逐段落: 键命中 → 复用 ILine[]（跳过元素构建与断行）
      └─ PageBreaker.breakPages(全部 ILine)   // M2b 才从首个脏页开始
  → HitTestIndex.rebuild(pages)              // M2b 才能按页重建
```

M2b 目标形态:

```
CommandManager.execute
  → patch.invalidation + dirtyNodeIds
  → document:changed
  → Draw.recomputeLayout(pool, invalidation)
      ├─ canIncremental(invalidation, dirty) ?
      │    ├─ yes → IncrementalLayoutEngine.relayout(doc, pool, dirty, firstDirtyPage)
      │    └─ no  → LayoutEngine.fullLayout()
      └─ hitTestIndex.rebuild(range)   // 仅重建受影响页
```


`HitTestIndex` 也要支持按页重建；当前是 `rebuild(pages)` 全量（Draw.ts L279）。

## 4. 验收

### 4.1 等价性（硬门）

- 新增 `IncrementalLayoutEquivalence.test.ts`：
  - 固定随机种子生成编辑序列（输入/删除/拆段/合并/样式/列表/表格 cell）；
  - 每步分别跑「全量」与「增量」，对 SLIF 做确定性深度序列化后**逐字节比较**；
  - 至少 500 步、覆盖页眉页脚变体与脚注。
- 任何不一致即失败，不允许用「视觉一致」替代。

### 4.2 性能（软门，记录不设卡）

- 1000 段 / 50 页文档，单字符编辑：`fullLayout` 当前耗时 vs 增量耗时（`PerformanceMetrics` 已有埋点）。
- 目标：增量 ≤ 全量的 25%；达不到就据实记录，不调低验收。

### 4.3 回归

- 既有 188 个测试文件全绿。
- 导出（JSON/TXT/HTML/OFD/CDA/元素）结果不变 —— 它们读的是同一份 SLIF/文档投影。

## 6. 风险

| 风险 | 处置 |
|---|---|
| 缓存键漏掉隐式依赖（主题 token、计算值、时钟） | 这些变化走全量；键里不出现，靠失效规则兜底 |
| 表格/脚注/域代码的跨页依赖 | 首版对表格块与脚注一律全量，跑通后再逐类放开 |
| `HitTestIndex` 与页面几何漂移 | 增量后按页重建；等价性测试同时比较命中索引 |
| 「看起来增量」再次误导 | 开关关闭时 `incrementalLayout` 不可被引用；文档与导出面只保留一个入口 |

---

## 7. 不做区

- 不恢复 `LayoutEngine.incrementalLayout()` 的旧实现（它仍是全量 + 对象复用，保留只为兼容，不接线）。
- `IncrementalLayout` 的 `paragraphKey` 已被 M2a 使用；它的实例缓存/`computeStats`、`LayoutCache`、`PageStartTable` 在 M2b 完成前仍**未被引用**，不得被当作已接线（契约 §16.1）。
