# 病历数据的"活"与"死"

> 同一份病历，在系统里是一条条带编码、可统计、可重算的数据；等它被导出成一段文字，看上去一模一样，价值却差了一个量级。

---

## 一、先看一个几乎每天都在发生的场景

医生在系统里写完一份入院记录。屏幕上读起来是一句很自然的话：

> 姓名：张三　性别：男　年龄：58 岁　体温：36.8℃

这句话里的每一个片段，来源其实都不一样：

- **"姓名："** 是模板里写死的固定文字，它就是文字；
- **"张三"** 是一条**带编号的数据**——控件库里给"患者姓名"配了数据元编码 `DE02.01.039.00`；
- **"36.8"** 是一个**数字**，不是"长得像数字的文字"。

所以，当这份文书被保存下来的时候，它其实同时以两种形态存在：**一种是程序可以继续使用的数据，一种是给人阅读的文字。**

大部分时候，这两种形态并不打架。麻烦出现在它**离开编辑器**的那一刻。

---

## 二、"活"的数据和"死"的数据，差在哪

抛开技术名词，一份"活"的病历数据，有三个特征。少了任何一个，它就开始"死"。

### 特征一：它有没有"身份"

病历里最容易做错的一件事，是把字段做成"看起来像表格的一段文字"。差别在哪？

有一份样例入院记录，里面有一个段落，结构是这样的：

```
"children": ["nd_mtv3xyxr_q", "nd_mtv9t084_7"]      ← 同一个段落里的两个节点

nd_mtv3xyxr_q  → { "type": "text", "text": "姓名：" }        ← 模板里的固定文字
nd_mtv9t084_7  → { "type": "smarttext", "text": "[姓名]",    ← 结构性字段
                   "element": { "code": { "dataElement": "DE99.99.001" } } }
                   （"value" 是运行时填入的患者姓名；未填时不写该字段，页面显示占位符「[姓名]」）
```

关键在于：**"姓名："这句文字和"患者姓名"这个字段，是在同一个段落里挨着的。**也就是说，字段可以嵌在一句话的中间——

> 患者**张三**，男，**58** 岁，因"反复上腹痛 3 天"入院……

读起来是通顺的文书，但它同时仍然是一条能被程序认出来的数据，带着自己的编码、名字和格式。

**排版上像文书，存储上是数据库——这两件事不必二选一。** 这是"活"的第一层。

### 特征二：它有没有"类型和值域"

同一个值，存进去的样子和显示出来的样子，可以不一样：

| 内容 | 存的是 | 显示的是 |
|---|---|---|
| 民族 | 代码（如 `hz`） | 汉族 |
| 体温 | 数字 `36.8` | 36.8℃ |
| 出生日期 | `YYYY-MM-DD` 格式的日期 | 2026-09-16（按需要格式化） |

这层价值不在于"好看"，而在于**它让系统有能力拒绝不合法的值**：该填数字的地方填了文字、小数位超出精度、长度越界——引擎会明确拒绝，而不是悄悄帮你四舍五入、或者把超长内容截断。

这一点我们在上一篇专门写过：**静默地把 `36.789` 存成 `36.79`，比直接报错危险得多。**

### 特征三：它能不能"重算"

病历里有 **8 类内容压根不是"写进去的文字"，而是"每次显示时才求值的表达式"**：页码、总页数、当前日期、当前时间、文档标题、作者、最后保存日期、打印日期。

举个最典型的：**页码。**

页码不是"第 1 页写个 1、第 2 页写个 2"。医生在前面补了一段，页数从 3 页变成 4 页，所有页码都要跟着重算。所以它存下来的必须是一个"域"，而不是一个数字。

> 一个很少被注意但很能说明问题的细节：正因为域是"算出来的"，所以在没有分页概念的导出稿里，页码、总页数这类域只能退化成固定值——当前实现按 1 页处理。

**身份、类型、可重算——三条都在，数据才是活的。**

---

## 三、"死"发生在哪一步：导出

引擎目前提供三种可用的导出格式，它们的分水岭非常清楚：

| 导出格式 | 导出的是什么 | 数据的状态 |
|---|---|---|
| **JSON** | 完整的结构化文档：节点、字段编码、运行时值、模板定义…… | **活** |
| **HTML** | 摊平后的文字与少量样式（粗体 / 斜体 / 下划线 / 表格合并） | **死** |
| **TXT** | 只剩文字 | **死** |

还是"姓名：张三"这一句。

**JSON 那一边**，它依然是一条带着身份的数据（就是上文那段结构）；**HTML 那一边**，它只是一行：

```html
<p>姓名：张三</p>
```

没有编码，没有值的类型，没有"这是哪个字段"的说明，也没有"这句话里哪几个字是可以被引用的数据"。

**它看起来完全一样，但它已经不再是一条数据了。**

这不是导出功能做得不好——**导出成 HTML/TXT 的本来目的就是"给人看"**，它就该是文字。真正的问题是：**很多团队默认"导出成功"就等于"数据还在"，于是把一份只适合阅读的产物，当成了系统的数据出口。**

---

## 四、为什么这件事值得较真

因为"死"数据的代价，从来不在归档那一刻，而在之后的每一次使用：

**1. 统计做不了。**
想算"这批患者的体温异常比例""某科室抗生素使用频次"，一堆文字帮不上忙，只能再找人录一遍。

**2. 复用做不了。**
同一份信息要上报病案首页、要生成随访记录、要进科研数据库，每换一个用途，就要重新敲一遍。

**3. 重排做不了。**
把一份 20 页的病历换个模板、调一版排版，活数据可以重排、重算；死文字只能重打。

**4. 追溯说不清。**
"谁在什么时候把哪个值改成了什么"——一张文字快照回答不了这个问题。

一句话概括：**"死"数据的成本，就是每一次"再录一遍"。** 而"再录一遍"这件事，在病历上从来不只是人工成本，它还会带进新的错误。

---

## 五、所以，导出不是"越简单越好"

理解了上面这件事，导出的策略其实就清楚了：

- **要打印、要交给患者、要长期版式归档** → 走**版式路径**（HTML / TXT，未来还有 PDF / Word）；
- **要统计、要上报、要复用、要迁移、要长期结构化保存** → 走**数据路径**（JSON）；
- **不要指望一条路径同时干好两件事。**

而且要注意：这两条路径**不是二选一**。同一份文书完全可以既导出成一张给人看的版式，又保留一份供系统使用的数据——**前提是源头那一份，从一开始就是数据。**

这也是我们一直在说的同一件事：

> 结构化不是让医生多填几张表，而是**让医生敲下的每个字，在需要的时候还能被用第二次。**

---

## 六、坦诚地说，我们仍在路上

这一节必须写清楚：

**PDF / Word 导出与多人协同仍在推进中，当前可用导出格式为 JSON / TXT / HTML。**

围绕本文主题，还有三点要如实说明：

1. **HTML / TXT 导出目前只承载内容，不含表格底纹、对齐等表现层样式。** 这是有意的取舍（表现层不属于内容导出），不是遗漏——但我们不打算把它说成"完整还原版式"。
2. **版本回溯与审计留痕，目前只走到"数据层"。** 仓库里已经有文档版本表、审计日志表的结构定义，也有一套**只升不降的文档格式迁移机制**（旧版本保存的文档能被升到当前格式再打开）；但对外可用的"版本列表 / 回滚 / 审计查询"接口与界面**仍在推进中**。我们不会把它写成"已完成能力"。
3. **那个"32 位编码"式的东西，也不是我们发明的。** 数据元编码来自医疗信息领域的既有标准与院方目录，引擎本身不硬编码任何医疗字典，而是由平台把真实目录注入进来——所以它能不能发挥作用，取决于接入方有没有一份认真维护的数据元目录。

我们更愿意把每一步走扎实，交付真正可用的能力，而不是一份好看的功能清单。

---

## 七、写在最后

病历数据最贵的地方，从来不是它被**写下来**的那一刻。

而是它被**第二次、第三次使用**的时候。

**一份只能被"读"的病历，只能服务一次；一份还能被"算"的病历，能服务很多次。**
