医生签字确认的是那张纸，不是屏幕——所以「预览的第 3 页」和「打印出来的第 3 页」之间，不该有任何解释空间。

打印一份三十页的病历，最容易出事的不是内容，是页脚。

这不是假设。仓库里躺着一条带注释的回归记录：打印稿里，页眉页脚整块消失，正文的页码域打印成了两个字面量——[页码]。屏幕上明明一切正常。原因也不复杂：打印走的是「另一条路」。

这一篇就讲清楚，「打出来和看到的一样」这件事，到底要同时做对哪几件事。

01

THE SECOND RENDERER

打印为什么最容易「走样」

打印出问题，八成不是因为排版错了，而是因为出现了第二个渲染器。

屏幕渲染和打印输出，天然像是两条路：屏幕画在可见的 canvas 上，打印要交给浏览器的新窗口、要落到纸上。很多实现在这里会「顺手再写一套」——一套给屏幕，一套给打印。于是同一份文档有了两个真相：屏幕上有页眉，打印稿里没有；屏幕上是「第 7 页」，纸上印着「[页码]」。

这套内核给自己立了一条硬约束：

「打印是渲染管线的投影，不得有第二个渲染器，也不得有第二份域代码解析。」

代码里的原话写得更直白——屏幕画布（render）与打印离屏（renderPageToContext）共用同一分派。（Draw.ts）

这条约束不是口号，它落到三个具体的地方。三个都做对，「一样」才成立；缺一个，就会回到上面那条回归记录。

02

THREE ALIGNMENTS

三件事同时做对，才叫「一样」

环节 要解决的问题 做错会怎样
同一份分页结果 一页装多少、在哪里断 屏幕第 7 页和纸上第 7 页装的内容不一样
同一条渲染管线 页眉页脚、域代码、批注怎么画 打印稿缺页眉、页码变字面量
同一批页面图 预览和打印读的是不是同一个东西 预览好好的，一点打印就换了个样

下面逐个说。

03

ONE PAGINATION

第一件事：分页先算准，而且必须是纯函数

打印一致的地基，是分页结果只有一份。

分页由 PageBreaker 负责，它是个纯函数：同样的文档 + 同样的页面设置（A4、页边距、页眉页脚），永远得到同样的分页结果——不多一页、不少一页、断点也一样。它不读浏览器、不读 DOM、不依赖当前视口。

真正难的从来不是「切页」，而是切得像人排的。这里有三条硬规矩：


孤行寡行控制

一个段落被拆到两页时，每一侧至少留 2 行。常量就一行：

. . . typescript

/** Minimum lines of a paragraph that must stay together (avoid orphans/widows). */

const MIN_PARAGRAPH_LINES = 2


跨页表头重复

长表格被切成多个 fragment 分到不同页时，第二页的表头要重新画一遍——否则读者不知道每列是什么。分页器在切页时把 headerLines 一路带着走。


表格是块边界

表格行不参与孤行寡行控制，它的跨页逻辑是另一套（以当前页剩余可用高去问表格分页器，拿回一个 TableFragment）。

相关代码：PageBreaker.ts（分页主体）、表格分页分支、孤行判定。

分页是纯函数，所以「预览第 7 页装什么」在算完那一刻就定死了——不会因为你换个屏幕、缩放下、换个窗口就变。这是「打印一致」能被保证的第一层前提。

04

ONE PIPELINE

第二件事：打印必须复用同一条渲染管线

分页算完，接下来是画。这里是最容易「分裂出第二个渲染器」的地方。

引擎的做法是：打印时不另写渲染代码，而是把每一页交给同一个渲染函数去画。preparePrintPages() 干的就是这件事：

. . . typescript

preparePrintPages(): string[] {

　const pages = this.draw.getPages()

　for (const page of pages) {

　　const offscreen = surface.createOffscreen(page.width * dpr, page.height * dpr)

　　// 渲染页面内容 (复用现有渲染管线)

　　this.draw.renderPageToContext(pctx, page, page.width)

　　result.push(offscreen.toDataURL('image/png'))

　}

　return result

}

关键在那句注释：复用现有渲染管线。而 renderPageToContext 自己的注释也写明了它必须包含什么——「与屏幕渲染（render）同源，必须包含页眉 + 页脚，并复用粒子管线（域代码逐页解析 / 控件 presentation 上下文）」。（Editor.ts、Draw.ts）

同一条约束还管到了别处。比如批注高亮——它没有走粒子管线，而是直接从文档的批注数据解析，理由写在注释里：屏幕（静态层）与打印（renderPageToContext）共用同一实现，保证两边一致。（Draw.ts）

还有一个反过来的要求：编辑标记不许进打印稿。不可见字符、编辑辅助线在屏幕上可以显示，打印时必须强制关掉——参数注释里写的是「打印必须强制 false（编辑标记不进打印稿）」。（Draw.ts）

于是那条回归记录的存在就很好理解了：它正是「有人绕开了同一条管线」的结果。修好之后，仓库里还专门留了一个测试文件守着这条线，文件头的注释就是那次回归的墓志铭。（PrintRender.test.ts）

05

ONE SET OF PAGES

第三件事：预览和打印，用的是同一批图

到这一步，「打印稿画对了」已经成立。但还差最后一环——预览和打印，读的是不是同一个东西？

如果预览是「重新排一遍给你看」，打印是「再排一遍拿去印」，那两边就有两次机会不一致。

引擎把这一环也掐掉了：预览和打印共用同一条输出路径。


点「预览」

setPrintPages(ed.preparePrintPages()) —— 生成一批页面图，预览窗口逐页显示其中的第 N 张。


点「打印」

openPrintWindow(selectPrintPages(all, range)) —— all 还是 ed.preparePrintPages() 生成的那批图。

EditorPage 里那句注释说得很清楚：打印与打印预览共用同一条输出路径——预览后点打印看到的就是这里的结果。（EditorPage.tsx）

打印窗口里的那几行 CSS 才是「最后一米」：

. . . css

@page{size:A4;margin:0}

img{width:210mm;height:auto;page-break-after:always}

意思是：纸张就是 A4，页边距为零；一张图就是一页，宽度锁死在 210mm（A4 的宽），图与图之间强制分页。 浏览器拿到的是已经排好的整页图，它不再重新断行、不再重新分页——它只负责把图印到纸上。

这也解释了一个细节：预览对话框在深色外壳下，中间那块纸面仍然是白的，代码里还专门留了豁免标记——「A4 纸面本体，打印必须 WYSIWYG」。（PrintPreviewDialog.tsx）

06

WHAT REALLY WORKS

打印对话框里，哪些是真的生效

「打出来一样」还有个容易被忽略的前提：你在对话框里填的，得真的被用上。

这里要说一句实在话，因为应用侧能管的和不能管的，界限很清楚：


页码范围是真的生效的

用户填的范围会先被钳到 [1, 总页数]，再按范围切片，然后才交给打印窗口。代码注释里留了一句自查：「原先这里直接丢掉 settings —— 页码框、续打断点全是摆设。」（printJob.ts、EditorPage.tsx）


打印机、份数、单双面

由系统打印窗口生效。JS 无法操控浏览器原生打印对话框，所以这三个控件的作用是「把用户的选择带进打印历史」。界面上有如实说明，没让人误以为在这里选了份数就生效了。（PrintDialog.tsx）


续打断点的语义

是「这一轮有没有打到末页」，而不是「浏览器有没有弹完打印窗口」（那个信号 JS 拿不到）。没打到末页，才留一枚断点，下次打开提示从下一页继续；打完了还留断点，会让人误以为要续打。（printJob.ts）

顺带一提，「打印模式」（print）在这套引擎里是一种只读模式——进到打印模式后，编辑是被锁住的，只能看、只能打。（EditorRuntimeState.ts、KeyboardHandler.ts）

坦诚与边界

老规矩，把边界说清楚——尤其打印这件事，最后一米并不完全在应用手里：


打印输出是「页面图」，不是矢量 PDF

每一页是渲染成 PNG 再交给打印窗口的，分辨率取决于页面像素尺寸与设备像素比；它不是矢量格式，不存在「无限放大不失真」。


最后一环仍在浏览器和系统手里

系统打印窗口里的「缩放」「适应纸张」这类设置会二次缩放，应用侧控制不了；要打出一比一的效果，那些选项需要保持默认（100% / 实际大小）。


分页靠 page-break-after 交给浏览器

这是浏览器打印路径，不是 PDF / PostScript 级别的分页控制；页面图高度与 A4 比例一致时是一图一页，但这条链路本身不是「绝对物理分页」。


页面图渲染复用主渲染管线

所以主渲染的边界它都有。例如文本塑形目前仍用 Canvas measureText，更高精度的塑形引擎是规划项。
