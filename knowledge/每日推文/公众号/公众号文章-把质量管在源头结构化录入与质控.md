# 病历质量，不是查出来的，是录进去的

> 质控科月末抽查、病案室集中返工——如果质量总是"事后"才被发现，那它从一开始就没有被管住。

---

## 一、一个月底的场景

每到月末，很多医院的画面是这样的：

质控科从系统里抽一批病历，逐份翻看：标题缺了、正文空了一段、必填项没填、字数明显不够……挑出问题，退回科室，医生重新翻出那份写了一半的病历，回忆当时的情况，补上。

这中间消耗的不只是时间。**返工发生在几天之后**，那时候医生手上已经有了别的患者；**补写的内容，靠的是回忆**；而**返工的过程，本身也不会让下一份病历写得更好**。

更麻烦的是，这类问题往往算不上"严重"，但数量极多。它们单个看起来都不值得退回重写，攒在一起却足以让一份病历的质量评价掉一个档次。

问题出在哪儿？

**出在"质量"被当成了一个末端环节。**

---

## 二、事后查，救不了三件事

把质量检查放在归档前，看起来是最省事的做法——不打扰医生书写，集中处理。但它天然解决不了三个问题：

**第一，返工成本远高于当场修正。**
一个字打错的空格，在书写时改掉是 1 秒；在三周后的质控环节退回来，是几分钟，而且需要重新进入那份文书的情境。

**第二，事后检查拿不到"原始数据"。**
病历里的关键信息如果只是"一串带格式的文字"，检查就只能停留在字面。想统计"这批患者的体温异常比例""该科室抗生素使用频次"，文字帮不上忙。

**第三，检查结果沉淀不到书写行为里。**
同一个错误在这个月被退回，下个月换个医生还会再犯——因为提示从来没有出现在他录入的那一刻。

所以真正要改的，不是检查的力度，而是**检查发生的位置**。

---

## 三、把质量往前挪，只有两步

我们做这个开源电子病历编辑器时，把"质量"这件事拆成了两个动作，都放在**源头**：

**一是让关键信息从录入那一刻就是数据；二是让问题在书写时就暴露出来。**

这两件事听起来朴素，但落地需要引擎层的支撑。

---

## 四、第一步：录入即数据

在**设计态**里，一份病历的关键字段不是"留一段空白让医生自由写"，而是可以被定义成明确的控件。当前引擎支持 **8 类结构化录入控件**：

| 控件类型 | 典型用途 |
|---|---|
| 单行文本 | 姓名、证件号、电话 |
| 多行文本 | 主诉、现病史、既往史 |
| 数字 | 体温、血压、检验值、剂量 |
| 下拉选择 | 分级、分类等固定选项 |
| 日期 | 出生日期、手术日期 |
| 日期时间 | 抢救时间、记录时间 |
| 复选框 | 症状、伴随表现（可多选） |
| 单选框 | 是/否类判断 |

差别不在于"看起来像表单"，而在于**写入的值会被校验**。

引擎把每个控件的值当成有类型、有值域的数据来对待，写入前统一过一道校验，**不合法就明确拒绝，而不是悄悄帮你改**。当前明确了 7 类拒绝原因：

- **写锁**：只读控件拒绝任何写入，包括清空；
- **类型不符**：该填数字的地方填了文字；
- **不在候选内**：下拉/单选的值不是声明的候选项；
- **超出精度**：小数位超过允许位数——**拒绝，不四舍五入**；
- **长度越界**：超出限定长度——**拒绝，不截断**；
- **日期格式不符**：要求 `YYYY-MM-DD`；
- **日期时间格式不符**：要求 `YYYY-MM-DD HH:mm:ss`。

> 这里有个容易被忽略的设计取向：**"不四舍五入、不截断"**。
>
> 静默地把 `36.789` 存成 `36.79`，或者把超长内容砍掉一截，表面上"写入成功了"，实际上医疗数据已经和医生填的不是一个值。对病历来说，这比直接报错危险得多。

另外，"必填"这件事也被单独拆了出来：**输入过程中允许留空，不打扰；到了保存、提交这类"完成时刻"才判定是否完整。** 医生不会因为第一秒没填完就被弹窗拦住。

---

## 五、第二步：问题在书写时暴露

引擎内置了一套文书质控检查，当前包含 **6 条内置规则**：

| 规则 | 严重度 |
|---|---|
| 标题不为空 | 错误 |
| 正文包含内容 | 错误 |
| 无连续空段落（正文与页眉页脚各自独立判定） | 警告 |
| 必填结构化字段不为空 | 警告 |
| 字数不低于最低阈值 | 提示 |
| 段落数在合理区间（1–500） | 提示 |

检查结果不是简单地"列一堆问题"，而是**先算分、再分级**：

- **100 分制**：每个错误扣 15 分、每个警告扣 5 分、每个提示扣 2 分，下限 0、上限 100；
- **四级评定**：≥90 分为 A，≥75 分为 B，≥60 分为 C，其余为 D；
- **三级问题列表**：错误 / 警告 / 提示分别计数，问题条目可定位到具体位置。

这样做的好处是：管理者看到的是一个**可比较、可追踪的分数**，而不是一堆口径不一的描述；医生看到的是**"还差多少分"以及差在哪里**。

更重要的是，**规则是可以扩的**。引擎在构造时接受一组自定义规则，与内置规则合并生效——也就是说，**医院自己的专科规则、病案首页规则、评审细则，都可以按同一套机制接进来**，而不需要改引擎。

---

## 六、还有一件事：别让规范变成负担

结构化录入和质控，本质上都是在"要求医生做得更多"。如果规范书写本身要额外花时间，那就是失败的。

所以配套还做了**医学缩写自动更正**：内置 **25 条**常用医学缩写规则，覆盖静脉给药、用药频率、时间与用法、常用指标四类。举个例子：

- `i.v.g.t.t.` → 静脉滴注
- `t.i.d.` → 每日 3 次
- `p.r.n.` → 必要时
- `SpO2` → 规范写法

医生照平时习惯敲缩写，系统在光标处自动识别并替换，**书写速度不变，规范度上去了**。

---

## 七、坦诚地说，我们仍在路上

这一节是必须写清楚的：

**PDF / Word 导出与多人协同仍在推进中，当前可用导出格式为 JSON / TXT / HTML。**

关于本文主题，也有两点需要如实说明：

1. **内置的 6 条规则，是一套"通用底线"，不是临床质量的全部。** 它覆盖的是标题、正文、空段、必填、字数、段落数这类所有文书都该满足的条件。真正贴合业务的规则（如专科必填项、时限要求、术语规范），需要按医院自己的口径扩展——引擎已经预留了扩展入口，但**规则内容本身，必须由院方定义**。
2. **质控引擎与结果面板组件都已在开源代码中实现（含评分、分级、问题定位），但主界面上的常驻入口仍在接入中。** 也就是说，能力是真实存在的、可被调用的，但"打开编辑器就能看到那个质控面板"这件事，我们还没做完，不打算含糊过去。

我们更愿意把每一步走扎实，交付真正可用的能力，而不是一份华而不实的清单。
