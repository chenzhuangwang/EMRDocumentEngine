QUOTE

质控科问的那句话，答案不该靠打电话。

「这份病历第 3 页的诊断，是谁改的？什么时候改的？改之前写的是什么？」

这三问，几乎是所有病历审计的起点。答不上来的结果很熟悉：翻纸质、打电话、问当事医生，最后勉强拼出一条时间线。

这篇不讲法规，只讲一件事：这套引擎现在能答出这三问里的哪几问，答不出的那部分卡在哪一步。

先把话说明白：本文只陈述引擎的能力现状，不构成任何法规条款的合规结论。三问本身是通用工程框架，不代表某项具体规范的要求。

01

FOUR QUESTIONS

把“留痕”拆成四个能分别回答的问题

“留痕”是个笼统的词。拆开看，它其实是四件事，而且这四件事的完成度完全不同：

你要回答的问题 对应的能力 现状
改了啥？ 版本比对（差异计算） ✅ 已做
能不能看到“改动过程”？ 修订标记（track changes） ⚠️ 只到渲染，编辑流未接
谁改的、什么时候？ 审计日志 ⚠️ 表结构就位，自动写入未接
归档后还能不能再改？ 只读 / 打印模式 ✅ 已做

下面四节，一节讲一个。

02

THE DIFF

“改了啥”：差异是算出来的，不是看出来的

审计最常问的一句是“这一版和上一版差在哪”。

引擎里对应的是文档比对：对两个版本的文档做差异计算，输出结构化的变更项（新增 / 删除 / 修改），再由对比视图可视化呈现，路由形如 /compare/:oldId/:newId。

“算出来”和“看出来”的区别很关键：


人工核对

逐字核对一份三十页的病历，不现实，而且会漏。


算出来的差异

可枚举、可定位——它不依赖任何人“看仔细一点”。

配套的是版本管理：文档的历史版本有记录、可回溯，后端也有对应的版本实体与数据访问层，让“调出某一版”有地方落。

「所以第一个问题，“改了啥”，是能答的。」

03

TRACK CHANGES

“改动过程”为什么最难：它是编辑流问题，不是打印问题

修订标记（track changes）是四个问题里最容易被误判的一个——因为它看起来“已经做完了”。

确实，标记本身已经能画，而且是按语义分颜色的：

语义 颜色令牌 色值
插入 revisionInsert 绿
删除 revisionDelete 红
修改 revisionModify 蓝

颜色的优先级链也是固定的：修订色 > 文档自身的字色 > 主题正文色 > 兜底黑。

也就是说，只要一个文本片段被标上了“这是修订”，它就不再是普通正文——它必须“看起来像修订”。

更值得说的一个细节：打印时这三种颜色会被统一收成黑色。

而且它不是靠 if (打印中) 用黑色 这种判断实现的，而是靠一整套 print 颜色令牌预设：同一份渲染代码，换一套令牌，所有颜色一起变。

REFERENCE

print 预设自己的注释只有一句：“灰阶 + 高对比 —— 所见即打印”。在这个预设里，修订三色被设成 0 0 0，注释写明理由：“打印无修订色语义，收成黑”。

但同一个预设里，批注高亮被刻意保留——注释写的是“黄色批注高亮仍保留（打印上有助批阅）”。

这个区别想清楚挺重要的：


修订色是“编辑过程”的产物

归档打印的正式文书上，不该留着一行绿的“这是新加的”。


批注是“要给人看的意见”

打印出来正好方便批阅。

「画笔有了，颜色也会随场景收放。问题在于——没有人在画。」

一个可以自己验的事实：全仓库里涉及“修订”的文件只有三个——颜色令牌定义、负责画文本的那个粒子、以及它的单元测试。没有任何一处是“产生修订标记”的编辑流程。

所以现在的实际状态是：正常编辑文档，不会自动生成“谁改了哪一处”的留痕。渲染能力就绪，上游编辑流没接上。

04

THE AUDIT LOG

“谁、什么时候”：表结构有了，写日志的人还没上岗

这一问对应审计日志。

后端的结构是就位的：审计日志的实体包含文档、用户、动作、详情、IP、时间六个维度，也有对应的数据访问层——也就是说，“一条日志该长什么样”这件事已经定义清楚了。

缺的是那个“写日志的人”：没有把“每次操作自动写一条”的拦截器接上。

所以现在的答案是：结构就位，自动写入未接。

这不是“差一行配置”，而是“还没有人决定哪些操作要记、记到什么粒度、写入失败时是否要阻断业务动作”。这些问题想不清楚就硬接，只会得到一堆“有日志但没人看、要查时查不到”的记录。

05

THE FREEZE

反倒是“归档之后”这一环，最实

前面三问都有缺口，第四问反而是最完整的：归档之后，不可改。

引擎提供只读模式与打印模式：进入归档态后编辑被锁死，只能看、只能打。技术上的实现很朴素——在按键处理的最上游，readonly / clean / print 三个模式都会被判定为“限制编辑”，编辑类操作直接不放行。归档即冻结。

还有一个容易被忽略的东西：导出副本的溯源标识。

一份病历一旦导出成 HTML / TXT / JSON，就“流出了系统”。为了让流出去的副本还能查来源，导出物里会带一个标识：


零宽字符编码

显示宽度为 0，不改变渲染、不影响搜索。


额外写入标识

HTML 里额外写入可读的 <meta>，JSON 里写入 _provenance 字段，记录生成器与版本。

NOTE

但这里必须诚实说清楚：这是取证备用手段，不是防盗手段——标识可以被一条正则一次性剥离。真正的证据底座，是前面说的版本历史与时间戳，不是这枚“水印”。

把它当成“防盗”来用，是要出事的。

06

ANNOTATIONS

批注：意见挂在正文上，但还缺一个“新建”

除了改，还有一种“痕迹”是不改正文、只提意见——批注。

引擎的批注带着线程 ID 与文本范围，能展示、能回复、能解决，并在正文对应位置以黄色高亮标出。意见和正文对得上，不靠“另附一张纸”——而且前面说了，这个黄色高亮打印时不会被收掉，正好方便在纸上批阅。

但同样要补一句：批注面板已具备展示 / 回复 / 解决的能力，当前还没有“新建批注”的交互入口。

这是界面层明确的待补项。

08

WHY SO DETAILED

为什么这篇要写得这么细

因为“留痕”这件事最怕口径含糊：


说“支持留痕”

读者会以为编辑时就会自动标出改动——那是没有的。


说“有审计日志”

读者会以为可以查到每一次操作——那也没有。


说“有溯源水印”

读者会以为法律上就算数了——那是过度承诺。

把“哪一层做到了、哪一层没做到”写清楚，比一句“我们支持审计留痕”负责得多。能力边界说清楚，用的人才知道什么时候该另做兜底。
