# 病历编辑器被问最多的 5 个问题

> 前面连着写了三篇内核（三层 Canvas、断行分页、Command 撤销）。这一篇换一个节奏：不讲架构，就集中回答这几个月评论区、私信、Issue 里反复出现的 5 个问题。答得不一定会让你"心动"，但每一句都对得上代码。

写系列文章有个好处，也有个"麻烦"。

好处是，写多了以后，读者问的问题开始**收敛**——翻来覆去就是那么几个；麻烦是，同样的话我得在评论区、私信里重复解释好几遍。

与其一遍遍打字，不如**集中回答一次**，也可以顺便把口径固定下来：以后哪里说得含糊了，大家翻这一篇就行。

下面这 5 个问题，是这段时间出现频率最高的。我的原则只有一条——**能做的就说能做，没做的就说没做，规划中的就标规划中。** 不吹，也不装。

## 一、"为什么不用现成框架？Quill、ProseMirror 不香吗？"

这是被问得最多的一个，也是我最想认真回答的一个。

先说结论：**现成的富文本框架非常好，它们解决的问题是"网页里怎么把文字编辑得顺滑"。** 但如果你的目标是"医院里一份能进病历、能签字、能归档的文书"，会发现有个东西对不上——**分页。**

网页富文本是**流式**的：内容有多少，页面就往下长多少，滚动条无限延伸。而病历不是流式的，它是**分页**的：A4 纸一张一张往下排，第 3 页底部放不下的一段，得整段落到第 4 页，还得处理孤行寡行、跨页表头重复——因为**打印出来的那份，才是要签字归档的那份**。

这两件事的核心诉求不同：一个要"随内容自适应"，一个要"和纸面严格对齐"。现成框架大多把"分页"当作可选项或后期插件，而在这套内核里，**分页是正确性的第一需求，是排版管道的骨架。**

除此之外还有两个直接原因：

- **结构化是刚需。** 病历里的字段（血压、诊断、用药）不是随便一段文字，它们要能被拆出来、能被质控规则扫描。基于 HTML 的内容模型做这个，得额外加一层映射；自研 Canvas 内核则可以直接把字段作为一等公民。
- **渲染要可控。** 三层 Canvas 渲染、脏区裁剪、增量分页这套东西，是为了在"上百页文档 + 频繁编辑"下仍然不掉帧。这块如果压在别人的渲染器上，能优化的空间很有限。

这个话题我在《为什么不用 ProseMirror：自研 Canvas 内核的取舍》里展开写过，那篇讲的是具体的取舍清单，这里不重复。

**一句话版**：不是"现成的不行"，而是**病历这个场景，值得为"分页正确 + 结构化 + 渲染可控"重新做一次内核**。

## 二、"导出到底支持哪些格式？能导出 Word / PDF 吗？"

这个问题必须答得**非常具体**，因为这里最容易产生误解。

**当前实际支持三种导出格式：**

| 格式 | 状态 | 说明 |
|---|---|---|
| **JSON** | ✅ 可用 | 完整文档树序列化，内含 `_toc`（目录）与内容溯源标识 |
| **TXT** | ✅ 可用 | 纯文本逐段落提取，保留段落换行 |
| **HTML** | ✅ 可用 | 生成完整 HTML，加粗 / 斜体 / 下划线映射为对应标签 |

另外，**页面打印（Canvas 渲染结果直接打印）已经可用**——这一点对"要进病历"的场景其实很关键。

**那么 Word / PDF 呢？答案是：目前还没有，规划中。**

在导出对话框里，这两个选项现在是标记为"即将推出"的——也就是说，**界面上看得到入口，但后端还没有对应的生成逻辑，导不出真正的 `.docx` 和 `.pdf` 文件**。

我知道这是很多人最想要的——毕竟大部分医院的最终归档是 Word / PDF。所以这里我不打太极：**它是明确的、高优先级的待补齐项**，但**现在确实没有**。谁跟你说这版已经能导出 Word，那都是错的。

## 三、"协同编辑做了没有？能不能多个人一起改？"

同样直说：**没有做完。**

准确的状态是这样：

- 依赖**已经就位**——前端装了 `yjs` + `y-websocket`，后端也有 WebSocket 通道；
- 在架构契约里，它被明确定义为一个**「延后能力（deferred capability）」**：数据边界、接入点都留好了，但**实现后置**；
- **还没有接入编辑流**——也就是说，现在打开编辑器，仍然是单人编辑。

为什么先留着不做？因为协同不是"加个库"那么简单。真正的难点在冲突合并的语义：两个人同时改同一个结构化字段（比如同一格血压），谁赢、怎么合并、撤销栈怎么跨人——这些想不清楚，硬接上去只会做出"看起来能协同、一用就乱"的假协同。

所以我的选择是：**接口先留好、边界先固定，等编辑流稳定了再接。** 现在对外只能说"架构上预留了"，不能说"支持协同"。**如果你需要多人实时协作，目前的答案是：还不行。**

## 四、"能不能商用？协议是哪种？"

能聊这个问题的，基本都是在认真评估落地的团队。答案很清楚：

**这套内核以 MPL-2.0（Mozilla Public License 2.0）开源。**

MPL-2.0 的边界，对"能不能商用"这个问题来说，可以概括成三点：

- **可以商用。** 用它做商业产品、提供服务，协议不禁止；
- **可以闭源集成。** 你可以把它和你的私有代码一起打包发布，**不必**把你的整个产品开源——这是它和 GPL 系协议最大的区别；
- **但它有"文件级"的开源义务。** MPL 是**文件级 copyleft**：如果你**修改了**它的源文件，那些**被修改的文件**需要以 MPL-2.0 回馈公开；没改动过的文件、以及你自己新写的文件，不受影响。

一句更直白的话：**"用它做闭源产品"可以，"改它的文件然后假装是自己写的"不行。** 如果你的团队打算深度改造内核并闭源分发，**建议先让法务确认一遍**——这不是技术问题，但会直接影响合规。

## 五、"跟 XX（某产品）比怎么样？你们是不是更强？"

这个问题我最想"往回拉"一下。

**我不做排名，也不做贬损。** 原因不只是"守规矩"，更是因为——**编辑器能不能用，从来不是"谁更强"，而是"谁更适合你这类团队"。**

所以每次被问到对比，我的回答都指向同一张图：《病历编辑器选型地图：商业套件 / 开源内核 / 自研，各适合谁》。那里把三条路的成本结构摊开讲了：

- **商业套件**，买的是确定性——成熟、有人兜底，代价是不便宜、且能力上限跟着厂商的 Roadmap 走；
- **开源内核**，买的是起点——不必从 0 写一个富文本内核，代价是维护责任回到自己团队；
- **自研**，买的是上限和可控——代价是时间和一支核心团队。

这套内核属于"**开源自研内核**"这一类：既开放，又是从头写的。它适合谁？**适合有研发能力、且对分页正确性和结构化有硬要求的团队**；如果你要的是"排期紧、别出事、有厂商兜底"，那商业套件可能更省心——这不是客套，是真心话。

一句话：**别问"谁更强"，先问"我的团队能承受哪种成本"。**

## 写在最后

把 5 个问题连起来看，你会发现答案其实是同一个态度：

> **能做的，做好；没做的，写明"没做"；规划中的，标清"规划中"。**

- 不用现成框架——不是瞧不起，是**分页正确性**这个需求，逼着必须自研；
- 导出只有 JSON / TXT / HTML——**Word / PDF 在规划里，但现在没有**；
- 协同**没接入**——只留了接口；
- **MPL-2.0，可以商用**，但有文件级回馈义务；
- 不做对比排名——**只提供选型地图，适不适合由你的场景说话。**
