01

THE DIAGNOSIS

先别急着优化，先把「慢」拆开

性能问题最怕一句话总结：「就是慢。」慢在哪？慢在打开、慢在编辑、还是慢在滚动？这三件事的成因完全不同，混在一起谈，只会越优化越乱。

把它拆成三笔账：

症状 表面上像什么 真实成因
打开慢 文件太大 全量排版 + 全量绘制
编辑卡 电脑不行 全量重排 + 全量重绘
滚动卡 显卡不行 所有页重画一遍

看出规律了吗？三笔账背后是同一个坏习惯：每次都从整篇文档重新算、重新画。所以真正要做的，不是「把每次重算变快一点」，而是让绝大多数重算根本不发生。

下面这六道防线，就是围绕这一句做的。

02

SIX DEFENSES

六道防线

防线一：只画看得见的那一屏

几十页的病历，用户屏幕上一屏其实只看得到一两页。那为什么要画几十页？

引擎用视口虚拟化解决：根据滚动位置和视口高度，算出「当前可见页范围」，再往前、往后各多留 1 页作为缓冲（overscan，防止快速滚动时白屏）。渲染时只画这个范围内的页，屏幕外的页直接跳过。

代码上，可见范围由 VirtualViewport 的 computeVisible() 计算，渲染入口 Draw.render() 只对可见页派发绘制。

「一句话：屏幕外的东西，再贵也与我无关。」

防线二：一帧只画一次

屏幕刷新是 60Hz 上下，一帧大约 16ms。如果连续输入时，每敲一下都立刻请求一次重绘，一帧内可能被请求十几次——而这十几次里，只有最后一次的结果会被用户看到。

引擎用 rAF（requestAnimationFrame）合并：把重绘请求「挂」到下一帧，同一帧内不管来多少次请求，只执行一次。

. . . typescript

scheduleRender(pool?: NodePool, runtimeState?: EditorRuntimeState): void {

　if (this._rafId !== null) return // 已有待执行的渲染帧

　this._rafId = this.host.surface.requestFrame(() => {

　　this._rafId = null

　　this.render(pool, runtimeState)

　})

}

关键在于那句 if (this._rafId !== null) return：只要已经排了一个帧，后续调用全部丢弃。 渲染次数于是被压到「显示器刷新率」这个上限，而不是「用户敲键盘的速度」。（Draw.ts）

防线三：只清变化的那一小块

Canvas 每帧重绘前，通常要先把旧内容清掉。如果每帧都把整屏清一遍再重画，擦除本身就是浪费。

引擎支持脏区裁剪：把「本次真正会变的矩形范围」标出来，重绘限定在这个范围内，其余部分不动。见 Draw.setDirtyRect()。

能不擦的地方就不擦，能少画的地方就少画。

防线四：改一个字，只重排那一段

这是整套优化里收益最大的一条。

排版（断行、分页、算高度）是 CPU 密集型操作。一份 2000 行的病历，段落上千个，如果每次编辑都从头重排全篇，慢是必然的。

引擎的做法是增量排版：给每个段落缓存一份排版结果（CachedParagraphLayout），编辑发生时，只对「变脏」的段落重新排版，干净段落直接复用旧结果。

. . . typescript

computeStats(bodyChildren: string[], dirty: DirtyTracker): { reused: number; recomputed: number } {

　let reused = 0; let recomputed = 0

　for (const paraId of bodyChildren) {

　　if (this.isValid(paraId, dirty)) reused++

　　else recomputed++

　}

　return { reused, recomputed }

}

配合「页面起始段落表」（PageStartTable）记录每页从哪段开始，分页也只重算受影响的页边界。于是改一个字的代价，从「重排一千段」降到「重排一段 + 重算几页」。（IncrementalLayout.ts、功能清单第 100 条）

防线五：让「谁脏了」这件事有据可查

增量排版要能工作，前提是得知道哪些段落脏了。这条信息由脏区追踪器维护，且分三层：


段落级

哪个段落内容变了。


页面级

哪些页需要重排。


节点级

哪个节点脏了（供质控、智能文本这类下游用）。

关键是它是自动的：命令执行之后，由命令管理器统一打标记，不需要各个功能自己手动喊「我脏了」。（DirtyTracker.ts、功能清单第 101 条）

脏区这套账记准了，前面两道防线才站得住。

防线六：连续输入，只算一步

这条同时解决了「卡」和「撤销难用」两个问题。

连续敲字时，如果每个字符都当一次独立操作，撤销栈会被瞬间塞满——按一次 Ctrl+Z 只撤回一个字，体验极差。而且每次都是一个待重排的脏区。

引擎用 500ms 自动合并窗口：相同类型、相同作者、时间差在 500ms 内的同类操作（连续输入、连续删除），自动合并成一个不可分割的操作。

. . . typescript

private readonly MERGE_WINDOW_MS = 500

// ...

if (next.timestamp - last.timestamp > this.MERGE_WINDOW_MS) return false

于是一段连续输入，既是一次重排触发，也是一步撤销。（CommandUndoRedoStack.ts、功能清单第 81 条）

补充一句：三层 Canvas（static / content / interact）把「光标闪烁」和「正文重绘」拆开，也是性能设计的一部分——这部分在系列第 11 篇《三层 Canvas 渲染架构》里详细讲过，这里不重复。

03

THE MEASUREMENT

怎么知道真的快了

优化最怕「感觉快了」。所以引擎内置了性能埋点（PerformanceMetrics.ts），采集四个关键指标：


渲染帧耗时（render_frame）


布局耗时（layout）


击键延迟（keystroke）


缓存命中率（cacheHitRate）

汇总时还会算 P95 渲染帧耗时——平均值会被大量「快的帧」稀释，P95 才能反映「最慢的那批帧到底多慢」。

这里必须如实说明三点，否则就成了「看起来很专业」的摆设：

1

默认不采集：埋点框架已就绪，但需要显式调用 startAutoFlush(url) 指定上报地址后才会开始定时采集（默认 30s 一批），并经 sendBeacon 在页面卸载时补发。没接上报地址，它就只是在内存里记数。

2

缓存命中率目前是占位值：summarize() 里 cacheHitRate 直接返回 100，注释写明「外部注入」——真实命中率统计还没接上。

3

样本上限 500 条：超出后滚动丢弃最旧记录，只保留最近窗口。

「换句话说：「怎么测」这件事已经搭好了，「测出来的数」还需要接上报与补统计，才算闭环。」

还欠着的，一并说清

本文的 8s → 400ms 是场景目标口径，不是一次标准化压测的结果；在拿到可复现的复测数据之前，我不会把它写成结论。

THE END

写在最后

性能优化到最后，拼的不是某一个「神级技巧」，而是六件朴素的事叠在一起：只画该画的、一帧只画一次、只清该清的、只重排该重排的、把脏区记准、把连续操作合并。没有哪一件单独拎出来惊艳，但它们凑在一起，才让「从 8s 到 400ms」这个量级有了着落——而具体数字，我留到有复测证据的那天再说。
