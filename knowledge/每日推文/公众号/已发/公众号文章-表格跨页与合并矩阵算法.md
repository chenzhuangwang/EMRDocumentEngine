# 表格跨页与合并矩阵算法：一张表格怎么"活"着穿过分页线

> 文字跨页，切一刀就行；表格跨页，切错一刀就是"半张表"。更要命的是，这张表里还藏着合并单元格——切在行边界只是第一道题。

写病历的人对表格一定不陌生：生命体征记录、用药医嘱、检验结果，几乎都是表格。一张入院记录里的"生命体征记录表"动辄二十几行，**它一定会穿过 A4 的分页线**。

问题就出在这条线上。如果分页器只会"整行换页"，第 8 行放不下就整个挪到下一页——本页底部留一大片空白；如果分页器粗暴地"拦腰截断"，一行字就横跨两张纸。而当表格里还有 `rowspan=3` 的合并单元格时，**从中间切开，下一页直接缺一格**。

这篇聊两件事：表格怎么**跨页**（TablePaginator），以及合并单元格怎么被**矩阵化**（MergeMatrix）。这是「EMR 文档编辑器」内核里，把"二维结构"塞进"一维页面"的完整解法。

## 一、表格跨页，难在哪

先说清楚为什么它比文字跨页难得多。

**文字是流式的**：段落由一行行文本构成，行与行彼此独立，在任意行边界断开，语义都不受损——所以分页器只需回答"这一行放不放得下"。

**表格是二维的**：它有行、有列，单元格还可能横跨多列（`colspan`）、纵跨多行（`rowspan`）。这意味着两件事：

1. **"行"不再是一个能自由切断的单位**。一个 `rowspan=3` 的单元格，逻辑上属于三行；如果只把其中一行切到下一页，这个单元格就没有宿主了。
2. **分页之后要能"重新接上"**。第二页开头的表，得让人看得懂——所以表头要重复；读者还得知道这是续表。

一句话：**表格跨页的本质，是把一个二维结构切成若干个"一维片段"，且每个片段都要自洽**。

## 二、三档分页策略：P0 / P1 / P2

这套引擎把表格分页写成了一个**纯函数分页器** `createTablePaginator(rows, columnWidths, opts)`——它不碰 DOM、不碰状态，只回答"给你这么多可用高度，你这一页能排出什么"。

它内部准备了三档策略，按"能整行就整行、实在不行才切行"的优先级降级：

```ts
// TablePaginator.ts
//   P0  行级跨页 — 整行放入直到放不下, 换页续排
//   P1  单行内切 — 单行超高 (无 rowspan) 按行边界切出 ≤ availableHeight 一片
//   P2  (rowspan 单元格行内切) — 显式不支持, hasRowspanCell 守卫跳过 P1
```

**P0 · 行级跨页**是默认路径。分页器从游标处往后累加"行单元高度"，直到放不下为止，整行整行地排。

```ts
// 整段 (rowspan span 或单行) 放入直到放不下
if (availForBody >= group.height) {
  let bodyH = 0
  let end = cursorRow
  while (end < bodyRows.length) {
    const g = groupHeight(end)
    if (bodyH + g.height > availForBody) break
    bodyH += g.height
    end += g.count
  }
  // ……
}
```

**P1 · 单行内切**对付的是"一行本身就比一页还高"的极端情况（比如一个单元格里塞了十几行说明文字）。这时按行边界切：

```ts
// 最大「落在 (from, upper] 内的行边界」; 若无 → 取首个 > from 的边界 (溢出一行, 保证推进)
let cutEnd = -1
for (const b of boundaries) {
  if (b > from && b <= upper) cutEnd = b
}
if (cutEnd < 0) cutEnd = boundaries.find((b) => b > from) ?? row.height
```

注意 `boundaries` 的取法——它来自单元格内各文本 item 的顶 y，**切在文本行之间，而不是文本行中间**，所以不会出现"半行字"。

**P2 · rowspan 单元格行内切**——引擎**明确不支持**。含 `rowspan` 的超高单元格被当成**不可拆分的原子单元**：整组同页，宁可视觉溢出，也不切断。

```ts
if (group.height > fullBodyAvail) {
  if (!hasRowspanCell(row)) {
    return sliceRowProgress(row, 0, availForBody, continuation)  // 纯单行 → P1
  }
  // 含 rowspan 的不可拆分 span → 整段独占一页, 允许视觉溢出
  const startIdx = cursorRow
  cursorRow += group.count
  // ……
}
```

这个"不支持"不是偷懒，而是一个**清醒的取舍**：跨页切开 rowspan 会让"合并语义"彻底破碎（下一页那一格既不属于上行也不属于下行），与其给出一个错误的结果，不如诚实地让它溢出。测试 `TablePaginator.test.ts` 里有一条断言专门锁死这个行为：含 rowspan 的超高行 `consumedRows === 1`、`height === 200`（页面只有 100 也整行独占）。

## 三、分页器为什么要"自持游标"

一个容易被忽略、但决定成败的设计：**分页游标不由外部传入，而是分页器自己持有**。

```ts
// 自持分页游标: cursorRow = 下一个待产出的完整 body 行; cursorYInRow = 当前行已切出的高度 (P1)
let cursorRow = 0
let cursorYInRow = 0
```

为什么这样设计？因为分页是"**逐页循环**"的：PageBreaker 只负责"每次给你当前页的可用高"，它**不理解 table / row / cell**，也不该去传 `startRow`。分页器把状态闭在内部，调用方接口就退化成一个极简契约：

```ts
paginate(availableHeight) → PaginateResult
  requiresNewPage = 本页放不下任何内容, 换页后再问 (显式状态, 非 height===0)
  done            = 整个表格已排完 (末行完整排完)
  consumedRows    = 本页实际完成的 logical body row 数 (P1 未完成为 0)
```

这里有一个**必须显式**的字段：`requiresNewPage`。注释写得很直白——"**显式状态，非 height===0**"。原因在于，如果让外部用"返回高度为 0"来判断该换页，就会遇到一个致命问题：**P1 切出的片段高度可能是 0 吗？不是。但"本页剩余放不下"和"这一页什么都排不出来"是两种完全不同的状态**，用同一个数值表达，分页器与 PageBreaker 之间就会出现"你不推进、我也不换页"的**死循环**。

PageBreaker 侧的消费逻辑因此非常克制：

```ts
// 本页放不下 → 结束当前页, 换页后再问 (游标未推进)
if (result.requiresNewPage) {
  // ……换页
  // 不前进 i — 同一 pageable 在整页可用高下必能推进 (TablePaginator 契约)
  continue
}
```

它**信任**分页器的承诺：只要给到"整页可用高"，就一定能推进。测试里那条"本页剩余不足 → requiresNewPage=true，换页后必能推进"的用例，锁的就是这条不变量。

## 四、重复表头：让第二页的表也"看得懂"

表格跨页后，第二页开头如果没有表头，读者根本不知道每一列是什么。所以 `pageBreak.repeatHeader` 打开时，分页器把**首行（表头行）单独抽出来**：

```ts
const headerCount = opts.repeatHeader ? Math.max(0, Math.floor(opts.headerCount)) : 0
const headerRows: SLIFRow[] = rows.slice(0, headerCount)
const bodyRows: SLIFRow[] = rows.slice(headerCount)
```

关键在于：**表头行是"视觉行"，不进逻辑行号**。每个片段都带上 `headerRows`，但 `logicalStart / logicalEnd` 只数 `bodyRows`：

```ts
logicalStart: headerCount + bodyStartIdx,
logicalEnd: headerCount + bodyEndIdx,
```

这样渲染时每页都能画出表头，但**行号、命中检测、编辑定位都不会因为表头重复而错位**——这是"重复表头"最容易踩的坑：把视觉上的重复行也当成逻辑行，翻页时光标就会跳来跳去。测试 `repeatHeader` 用例专门断言了这一点：第 1 片覆盖 `[1,4)`、第 2 片覆盖 `[4,5)`，表头行始终不占逻辑行号。

另一个细节是**行隙**。为了让分页、命中、渲染三方用同一套高度口径，引擎抽了一个共用函数：

```ts
/** 单行的布局占高 (行高 + 行隙) — 表格分页/命中/渲染三方共用, 避免漂移 */
export function tableRowUnitHeight(row: { height: number }): number {
  return Math.max(row.height || 24, 24) + TABLE_ROW_GAP
}
```

`TABLE_ROW_GAP = 1`。别小看这 1px：如果分页器算行高时不加它、渲染时又加，累计到第 20 行，表格底部就会和下一页的表格**重叠或留缝**。"三方共用同一函数"是刻意的——**避免漂移**。

## 五、合并矩阵：把二维结构压进一维数组

跨页解决了"切"，接下来是"合并单元格怎么表示"。引擎的答案是 `MergeMatrix`：**一个二维占位数组 + 一张 span 表**。

```ts
export class MergeMatrix {
  private matrix: (string | null)[][]        // 每个格子存"占用它的 cellId"
  private rowCount: number
  private colCount: number
  private spans = new Map<string, CellSpan>() // cellId → { colspan, rowspan, col, row }
}
```

放置一个单元格时，`placeCell` 先做**合法性 + 空闲检查**，再把整块区域**填成同一个 cellId**：

```ts
placeCell(cellId, row, col, colspan = 1, rowspan = 1): boolean {
  if (row + rowspan > this.rowCount || col + colspan > this.colCount) return false
  // 检查所有格子是否空闲
  for (let r = row; r < row + rowspan; r++)
    for (let c = col; c < col + colspan; c++)
      if (this.matrix[r][c] !== null) return false
  // 填充 ……
}
```

于是"某个位置是否被合并单元格占用"就退化成一个 O(1) 查表：`isOccupied(row, col)`。这正是排版时"跳过被占用列"的基础。

矩阵的构建函数 `buildMergeMatrix` 里藏着一个**踩过的坑**：

```ts
// 列数: 显式 numCols > sum(colspan) 推算。
// 修复 v21.0 前 max(cells.length) 在 colspan 下低估列数的问题。
const numCols = opts?.numCols
  ?? Math.max(1, ...rows.map(r => r.cells.reduce((s, c) => s + (c.colspan || 1), 0)))
```

早期用 `max(每行 cells 个数)` 当列数，一旦有 `colspan=2` 的单元格，**列数会被低估**，导致后续合并直接越界失败。改成 `sum(colspan)` 才是真实的网格列数。

矩阵还有一个用途是**命中反查**。点击表格时，一级命中只能定位到"整张表的外框"，要落到"具体哪个单元格"，就用 `findCellAt`：

```ts
// 用累积行高定位行 → 用累积列宽定位列 → 查矩阵得 cellId
if (row >= this.rowCount || col >= this.colCount) return null
const cellId = this.matrix[row][col]
if (!cellId) return null
const span = this.spans.get(cellId)
return { cellId, row, col, span }
```

坐标是相对于表格原点的逻辑像素，用累积高/宽逐格累加定位——**不依赖任何 DOM**，因此在 Canvas 渲染下同样成立。

## 六、三遍排版：单元格、行高、垂直对齐

矩阵构建好了，真正的排版在 `LayoutEngine.buildTableRows` 里，它把表格节点展开成 `SLIFRow[]`，分**三遍**走。

**第一遍**：逐行逐格布局内容，用 `colCursor` 跳过被占用的列：

```ts
let colCursor = 0
for (const cellId of row.children) {
  while (colCursor < columnWidths.length && matrix.isOccupied(ri, colCursor)) colCursor++
  if (colCursor >= columnWidths.length) break
  // ……布局 cell 内文本, 累加 colspan 列宽
  matrix.placeCell(cellId, ri, colCursor, cellSpan, rowSpan)
  colCursor += cellSpan
}
```

单元格宽度 = **它跨过的各列宽之和**（`colspan` 直接体现为宽度累加）。列宽本身按 `fixed > percentage > auto` 的优先级算——和 Word 的口径对齐。

**第二遍**：内容可能比行高更高（文本换行、多段落堆叠），需要**撑高行高**。这里 `rowspan` 的处理是关键：

```ts
const need = cl.contentHeight + CELL_PAD * 2 - (cl.rowspan - 1)
if (cl.rowspan <= 1) {
  if (rowHeights[cl.row] < need) rowHeights[cl.row] = need
} else {
  let spanH = 0
  for (let s = 0; s < cl.rowspan && cl.row + s < numRows; s++) spanH += rowHeights[cl.row + s]
  if (spanH < need) {
    const lastRow = Math.min(cl.row + cl.rowspan - 1, numRows - 1)
    rowHeights[lastRow] += need - spanH   // 缺口加到最后一行
  }
}
```

跨行单元格的"应得高度"是它覆盖的几行之和，缺的部分**统一补给最后一行**——这样前面几行的行高不被无谓撑大，视觉上更自然。

**第三遍**：构建最终的 `SLIFRow[]`，同时应用垂直对齐：

```ts
let contentTop = CELL_PAD
if (cl.verticalAlign === 'middle') {
  contentTop = Math.max(CELL_PAD, Math.floor((cellHeight - cl.contentHeight) / 2))
} else if (cl.verticalAlign === 'bottom') {
  contentTop = Math.max(CELL_PAD, cellHeight - cl.contentHeight - CELL_PAD)
}
```

`top / middle / bottom` 三种对齐，落成的是内容的**顶部偏移量**——渲染层只管照 y 画，不需要理解"对齐"这个概念。这就是"排版产物与渲染解耦"：LayoutEngine 算出精确坐标，渲染层无脑执行。

## 七、合并与拆分：一次改动的原子性

矩阵和排版都是"读"，用户还要能"写"——合并、拆分单元格。这部分在 `TableOps.ts`，有三类操作。

**单行相邻合并** `mergeAdjacentCells`：只支持同一行内左右相邻、且两侧都未跨行（`rowspan` 都等于 1），`colspan` 累加、内容并入、右侧单元格移除。

**框选矩形合并** `mergeRange`：框选一片区域，左上角单元格作为合并目标，`colspan × rowspan` 落成目标单元格的跨度。这里有一行**必须写对、写错就出大事故**的代码：

```ts
if (cell?.children?.length) {
  targetCell.children = [...targetCell.children, ...cell.children]
  // 关键: 清空引用, 防止 removeChild 级联删除已并入目标 cell 的段落
  cell.children = []
}
```

注意顺序：**先把待删单元格的 `children` 清空，再 `removeChild`**。否则 `removeChild` 会把它名下的段落一起级联删掉——而这些段落此刻已经被"并入"了目标单元格，等于把刚搬过去的文字又删了一遍。这是内容级联删除的经典陷阱。

**拆分** `splitCell` 分两个方向：水平拆分（`colspan` 减小、右侧新增单元格）与垂直拆分（`rowspan` 减小、下一行对应列新增单元格）。垂直拆分时要先在下一行里**按网格列找到插入点**，再插进去，保证拆分后的单元格落在正确的列上。

这三类操作都挂在 Command 模式上（详见系列上一篇《撤销栈与 Command 模式》），所以**一次合并 = 一次可撤销的改动**，用户按错 Ctrl+Z 能干净退回。

## 八、坦诚地说，现状

按惯例，把现状说清楚：

**PDF / Word 导出与多人协同仍在推进中，当前可用的导出格式为 JSON / TXT / HTML；导入侧支持 JSON / HTML / Markdown / XML。**

表格这块，也有几个必须如实讲清的边界：

- **P2 显式不支持**：含 `rowspan` 的超高单元格不做行内切，整组同页、允许视觉溢出——这是取舍，不是遗漏；
- **`continuationLabel`（续表标记）是保留字段**：`TableFragment` 里有 `continuation` 布尔量，但"续表"文字当前布局不再产出、渲染层也不再绘制；
- **`MergeMatrix.computeEffectiveColumnWidths` 目前只是拷贝**：真正按合并关系折算列宽的逻辑还没落进来，列宽折算目前由 `buildTableRows` 直接累加完成。

这些不是"差不多就行"的领域，而是"错一格、整张表就散"的领域。把边界摆出来，比装作没有更靠谱。

## 写在最后

回到开头那句话：文字跨页，切一刀就行；表格跨页，切错一刀就是"半张表"。

表格分页真正的功夫，落在四个词上：**降级**（P0 整行 → P1 切行 → P2 拒绝切，能整行绝不切行）、**自洽**（分页器自持游标、`requiresNewPage` 显式表达、绝不死循环）、**矩阵化**（用一张二维占位表，把"合并"这种二维关系压成一维数组可查）、以及**原子性**（合并拆分都是可撤销的一等改动）。

四件事合起来，才是一张能"活着穿过分页线"的表格。
