# 合规审计视角下的电子病历

> 前一篇回答的是"大家最关心什么"。这一篇换个视角——从**审计、质控、留痕**的角度，看一份电子病历里藏着哪些"看不见的坑"，以及编辑器能在这里帮上什么忙。

先设想一个真实的场景。

质控科的人坐在你对面，翻开一份病历，问：

> "这份病史，第 3 页的'诊断'是谁改的？什么时候改的？改之前写的是什么？"

你能当场答上来吗？

很多医院的答案是——**答不上来**。或者说，要靠翻纸质、打电话、问当事医生，才能勉强拼出一条时间线。而这，正是"合规审计"真正要解决的事。

## 一、合规审计，到底在问什么

抛开条文，审计的核心就三个问题：

1. **谁改的？**——身份；
2. **改了什么、什么时候？**——内容与时间；
3. **这条记录，能不能被验证、有没有被动过？**——完整性。

电子病历理论上比纸质**更该做到**这三件事：时间戳天然精确、操作天然可记录。但如果系统在最初设计时没把这三件事放进去，电子病历反而可能**比纸质更难追溯**——纸质还有笔迹，电子改完就"无痕"了。

所以合规审计的落点，从来不是"加一个日志文件"那么简单，而是——**一条能被独立验证的证据链。**

## 二、一条"证据链"，由哪几块拼起来

我习惯把它拆成四块：

| 拼图 | 它回答的问题 |
|---|---|
| **版本历史** | 这份文书一共经历了几版？每一版长什么样？ |
| **操作日志** | 谁、在什么时间、对哪份文档、做了什么动作？ |
| **溯源标识** | 这份导出的副本，出自哪个系统、哪个版本？ |
| **不可篡改** | 归档之后，还能不能偷偷改？ |

缺任何一块，证据链都是断的。下面如实说说：这套引擎，目前拼上了哪几块，还差哪几块。

## 三、已经做到的

### 1. 改前改后，能直接对比

审计最常问的一句是"这一版和上一版差在哪"。引擎里有**文档比对**能力：对两个版本的文档做差异计算，输出结构化的变更项（新增 / 删除 / 修改），再由对比视图可视化呈现，路由形如 `/compare/:oldId/:newId`。

增删改一目了然，不必人工逐字核对——**差异是算出来的，不是看出来的。**

### 2. 历史版本，可以回溯

配套的是**版本管理**：文档的历史版本有记录、可回溯。后端也有对应的版本实体与数据访问层，让"调出某一版"这件事有地方落。

### 3. 格式在演进，旧档不丢

这一点最容易被忽略，却直接关系到"档案能不能长期保存"。

病历是要**存几十年**的。如果文档格式升级一次、旧文件就打不开了，那所谓的"电子档案"就是空的。引擎把**文档格式版本**与**引擎代码版本**严格分开，并配了一条**链式升级通道**：

- 当前文档格式版本 **4.5.0**，与引擎代码版本（21.0.0）是两套独立编号；
- 升级链已注册 **8 段**（v1 → v2 → … → v4.5），打开旧文档时按链**逐段迁移**到当前版本。

**格式可以长大，但旧档要一直读得开**——这是档案保存的底线。

### 4. 过程不中断，记录才不会断

"改到一半断电，内容丢了"，在审计上等于**记录断裂**。

引擎的自动保存写在浏览器本地存储里：**3 秒防抖**触发，保留**最近 3 个版本**，并带**崩溃恢复检测**——下次打开时会提示恢复。过程连续，记录才连续。

### 5. 质控意见，能挂进文档

审核者不该直接在病历上"涂改"，正确做法是**批注**。

引擎的批注带着线程 ID 与文本范围，能展示、能回复、能解决，并在正文对应位置以**黄色高亮**标出——意见和正文对得上，不靠"另附一张纸"。

> 如实补一句：批注面板已具备展示 / 回复 / 解决的能力，但**当前还没有"新建批注"的交互入口**。这是界面层明确的待补项。

### 6. 导出的副本，能溯源

一份病历一旦导出成 HTML / TXT / JSON，就"流出了系统"。为了**流出去还能查来源**，导出物里会带一个**取证溯源标识**：

- 用零宽字符编码（显示宽度为 0，**不改变渲染、不影响搜索**）；
- HTML 里额外写入可读的 `<meta>`，JSON 里写入 `_provenance` 字段，记录生成器与版本。

必须诚实说明：这是**取证备用手段，不是防盗手段**——标识可以被一条正则一次性剥离。真正的证据底座，是前面说的**版本历史与时间戳**，不是这枚"水印"。

### 7. 归档之后，不可改

引擎提供**只读模式**与**打印模式**：进入归档态后编辑被锁死，只能看、只能打。归档即冻结——这是"不可篡改"最朴素的一层实现。

### 8. 权限，按角色来

后端是 JWT + Spring Security 的认证授权，用户带**角色**，接口按角色鉴权。谁能看、谁能改，从入口就分开。

## 四、还没接上的，也一并说清

如果只讲"已经有的"，那就不叫合规视角了。下面这几条，必须讲明白：

- **质控规则引擎：引擎在，接线没接。** 内置 6 条质控规则（支持自定义扩展）、能评分分级，代码与单测都齐——但它**在整个仓库里从未被实例化**，对应的结果面板也**从未被渲染**。一句话：**能力写好了，界面够不着。**
- **修改留痕（track changes）：只到"渲染"这一步。** 引擎已经能按"插入 / 删除 / 修改"三种语义给文本上色（打印时统一收成黑色）。但**产生这些修订标记的编辑流程没有接入**——现在正常编辑文档，不会自动生成"谁改了哪一处"的留痕。
- **审计日志：结构就位，自动写入未接。** 后端有审计日志的实体（文档、用户、动作、详情、IP、时间）和数据访问层，但**没有把"每次操作自动写一条日志"的拦截器接上**。
- **字段级脱敏 / 分级保护：规划中。**

把这四句和上面八条放在一起看，你才好判断：这套引擎在合规上**已经能承担什么**，以及**还不能承担什么**。

## 五、把"合规"翻译成"省事"

最后，落回场景。

合规不是给医生加负担。恰恰相反——**真正好的合规设计，是把"事后找证据"的麻烦，变成"事中顺手留痕"的自然。**

- 质控要追溯？不用打电话问医生，直接调两个版本做比对；
- 病案要长期保存？格式升级链保证几十年后还打得开；
- 审核要提意见？批注挂在正文上，闭环可查；
- 副本流出去了？溯源标识能指回出处。

**这些能力，不需要医生额外"操作一下"——它们应该长在编辑器里。** 这才是"合规"对一线真正的意义：不是多填一张表，而是少一次扯皮。

## 写在最后

合规审计这件事，说到底是在问一个朴素的问题：

> **"这份病历，经得起回头查吗？"**

这套内核在"能查"这件事上，已经铺了相当多的地基：**版本可比、历史可溯、格式可迁、过程可恢复、副本可溯源、归档可锁定**。同时，我也把**还没接上的那几根线**（质控接线、留痕编辑流、审计日志自动写入）原原本本写在了上面。

**地基，和管线，是两回事。** 我不会把"管线还没接"说成"已经通了"。
