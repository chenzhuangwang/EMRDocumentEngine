# 病历模板化书写：科室经验怎么沉淀

> 每个科室都有一套"心里的模板"——哪一栏放前面、哪些必须填、缩写怎么写。可它常常只活在几个人的脑子里，没写进系统。

---

## 一、一个几乎每个科室都遇到过的场景

新入职的住院医来问：我们科的《入院记录》模板在哪？

师兄头也没抬：没有模板，我发你一份上周写好的，你照着改。

三个月后，这份"模板"已经在科里传了七八手：有人删了一栏，有人加了一项，有人顺手把字号调大了一号，还有人把页边距改成了自己顺手的值。等到质控来抽查，谁也说不清"标准版"到底长什么样。

这件事的尴尬之处在于：**科室里其实是有"经验"的，但它没有被"沉淀"——它只是在人手里，被一代代手抄。**

这也是"病历模板化书写"这件事真正的难点：不是缺一个模板文件，而是缺一套**能把经验写下来、还能跟着一起走的机制**。

---

## 二、科室经验，为什么总是沉淀不下来

把上面那件事拆开，会发现卡点不止一个，而是三个叠在一起。

### 1. 经验本身是"默会"的

老主任知道"既往史里必须写清三件事"，知道"某类病人一定要记录过敏史"，知道"这个诊断的规范缩写怎么写"。

但这些都属于**他知道**，而不属于**系统知道**。它不在任何一份可以被检索、被继承的配置里。

### 2. 沉淀的载体错了：留下了"文档"，没留下"规则"

过去沉淀科室经验的方式，是把**一份填好的病历**存下来当范本。

问题在于：一份填好的病历，记录的是"这个病人写了什么"，而不是"这个字段该怎么填"。前者是**结果**，后者才是**经验**。拿结果当模板，下一个人只能照着猜。

### 3. 校验发生在"事后"，而不是"书写时"

必填项漏了、格式不对——这些问题的暴露时间，通常在质控环节，也就是**写完以后**。

于是流程变成：写完 → 检查 → 打回 → 重写。每一次往返，消耗的都是医生的时间和信息科的排期。

---

## 三、把"经验"翻译成系统能读懂的三样东西

关键的第一步，是先承认一件事：**任何一条科室经验，落到系统里，本质上无非三类信息之一。**

| 经验的样子 | 系统里对应什么 | 例子 |
|---|---|---|
| "这一栏代表什么" | 字段语义 | 姓名 / 入院日期 / 主诉 |
| "它长什么样" | 呈现形态 | 用输入框还是下拉、要不要带"姓名："前缀 |
| "能不能动、要不要填" | 约束 | 必填 / 只读 / 可删除 / 只能出现一次 |

只要这三类信息都能被配置，科室经验才有可能从"人的记忆"变成"系统的配置"。

而"配置"最怕的一件事，是把这三类信息**混在一起**——一旦混了，就会退化成"每次都得改代码"。

---

## 四、我们怎么做的：模板 = 文档 + 一层独立的设计期属性

在我们这套 **EMR 文档编辑器引擎**里，模板没有被做成"一团糊在一起的 JSON"，而是被拆成了清晰的分层。

### 1. 四层分离：各管各的事

| 层 | 回答的问题 | 存在哪里 |
|---|---|---|
| 语义层 | 这个字段"是什么" | 节点的语义信息（数据元编码、类型、名称） |
| 运行时值层 | 患者"写了什么" | 节点的值 |
| **模板设计期层** | 控件在模板里"长什么样、能不能动" | **一层独立配置，按节点 id 关联** |
| 表现层 | 怎么渲染 | 独立的表现样式 |

**为什么要分开？** 因为"模板"和"病历"本来就是两种东西：

- **模板** = 占位符 + 设计期配置（这个控件能不能删、要不要必填）；
- **病历** = 已经填好的值，**不该再带着"这个控件能不能删"这类设计期信息到处跑**。

一份填好的病历要归档、要上报，它身上不该背着只有模板作者才关心的那些开关。

### 2. 设计期属性，一共 8 个字段

落到代码里，这一层就是一个按节点 id 关联的小对象，字段总共 8 个：

| 字段 | 作用 |
|---|---|
| `label` | 控件旁的标签（如"姓名："） |
| `prefix` / `suffix` | 控件前 / 后渲染的字面量 |
| `tips` | 悬浮提示文案 |
| `deletable` | 设计期是否允许删除 |
| `editable` | 是否接受输入 |
| `single` | 该数据元在文档中是否唯一 |
| `controlType` | 控件形态（8 类之一） |

它的约束很硬：**这 8 个字段绝不写进文档本身**，而是作为独立的一层单独存储。

### 3. 存储：作为文档的"兄弟字段"，而不是塞进节点里

序列化时，这一层和文档节点是**平级的两个顶层字段**，绝不混进节点内容：

```json
{
  "nodes": { "...": {} },
  "templateDefinitions": {
    "<节点id>": { "label": "姓名：", "controlType": "input" }
  }
}
```

落到后端，整个模板（文档树 + 设计期配置）序列化成一段 JSON，存进模板表的一个字段里。**模板是数据，不是代码。**

## 五、配置动作：让"沉淀经验"变成点几下的事

拆完结构，再来看配置界面——它才决定科室经验能不能被真正"写下来"。

### 1. 控件库：一条目 = 语义 + 设计期

控件库里预置的是**结构化控件**，当前支持 **8 类**：单行文本、多行文本、数字、下拉选择、日期、日期时间、复选框、单选框。

每条控件库条目，本身就是**语义信息 + 设计期配置**的双载荷。插入一个控件，等于一次性把"这是什么字段"和"它该怎么配置"都带了进来：

- 选"日期"类数据元 → 默认落成日期控件；
- 选到"多值" → 默认落成复选框或单选框。

### 2. 属性面板：把经验逐条填进去

选中一个控件，属性面板可以就地编辑它的设计期属性：标签、前后缀、提示、是否必填、是否只读、是否可删除、是否单值。

**这一步，就是把"老主任脑子里的规矩"，逐条搬进系统的地方。**

### 3. 三条"守卫"：配置写下去，就真的生效

最容易变成摆设的，是"配了但不生效"。所以这几条约束都被写进了**命令层**——不是在界面上藏一下就算，而是底层直接拦住：

- **`single` 守卫**：某个数据元配了"唯一"，再插入一个相同数据元时，插入命令**直接拒绝执行**；
- **`deletable` 守卫**：配了"不可删除"的控件，删除命令**直接拒绝**；
- **`editable` 写锁**：配了"只读"，写入校验会拦下输入。

### 4. 必填怎么生效：书写时不管，完成时才判

一个很实际的取舍是：**必填项不该在医生敲第一个字的时候就报错。**

所以"必填"的判定被放在**完成校验**环节——输入过程中允许留空，提交时才判"必填却没填"。

而这个"必填"最终会被**质控引擎**消费：内置的 **6 条质控规则**里，就有一条专门检查"必填的结构化字段是否为空"。问题会在书写阶段被提示，而不是等归档时被打回。

> 📷 **配图位 ③**（真实截图）：质控面板的评分与问题列表，高亮"必填项未填"那一条。

## 六、沉淀下来之后，科室能拿到什么

回到开头那个场景。如果这套机制真的被用起来：

- **换人不换格式**：新人不用再"照着上一份改"，打开的就是标准模板；
- **经验从口头变成可查**：哪一栏必填、哪个字段唯一，写在配置里，不靠口口相传；
- **漏填在书写时就提示**：不必等到质控打回再返工；
- **改格式不用改代码**：模板是数据、不是代码，配好一次、一键套用，不必每次都走研发改版。

一句话：**把"传给下一个人的经验"，变成"传给下一个人的配置"。**

---

## 七、坦诚地说，我们仍在路上

按惯例，把现状说清楚：

**PDF / Word 导出与多人实时协同仍在推进中，当前可用的导出格式为 JSON / TXT / HTML；导入侧支持 JSON / HTML / Markdown / XML。**

还有一点要如实讲：模板"沉淀"这件事，引擎能提供的是**结构化的容器与配置能力**——能不能把经验真正沉淀下来，取决于使用方愿不愿意花时间，把科室的规矩一条条配进去。**工具负责让"沉淀"变简单，但它替代不了"沉淀"这个动作本身。**
