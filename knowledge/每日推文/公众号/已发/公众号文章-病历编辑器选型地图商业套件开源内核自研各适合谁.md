# 病历编辑器选型地图：商业套件 / 开源内核 / 自研，各适合谁

> 选病历编辑器，最怕的不是"没得选"，而是三条路都有人说好。这篇不做排名，只给一张能落地的决策地图。

"编辑器的技术选型，到底怎么定？"——最近这个问题被问了三次：一次来自正在做结构化改造的 HIS 厂商，一次来自准备替换旧系统的三甲信息科，还有一次来自想压低成本的中小团队。

答案有三套：有人推**商业套件**——成熟、省心、出问题有人兜底；有人劝用**开源内核**——免费、可改、社区活跃；也有人直接说**自研**——需求太特殊，别人做的迟早不够用。

三条路听起来都对。但选错的代价完全不一样：买错了亏的是钱和排期，自研错了亏的是**半年起步的时间，加一支要长期养的核心团队**。所以真正该问的不是"哪个最好"，而是——**"我这类团队，走哪条路的期望成本最低"**。

上一篇《电子病历编辑器怎么选？按成熟度分三梯队》盘点的是"市面上有哪些方案"；这一篇换个角度，聊"**买成品、用开源、自己做，这三条路分别适合谁**"。两篇配着看，一张是货架，一张是路线。

## 一、先给结论：三条路，本质是三种成本结构

把三条路并排看，差别不在功能多少，而在**你愿意把成本付在哪里**：

| 路线 | 你买到的是什么 | 主要成本付在 | 能力上限由谁决定 |
|---|---|---|---|
| 商业套件 | 确定性（成熟度 + 履约兜底） | 授权 / 年费 + 供应商绑定 | 厂商的 Roadmap |
| 开源内核 | 起点（不必从 0 开始） | 二次开发与长期维护人力 | 你团队的上限 |
| 自研 | 上限与可控 | 时间 + 一支核心团队 | 你的业务深度 |

一句话：**商业套件把不确定性换成钱，开源内核把不确定性换成人力，自研把不确定性换成时间。** 选型，就是选你更能承受哪一种。

## 二、路线一：商业套件——买的是"确定性"

商业套件（如 dcwriter、大成等成熟产品）最大的价值，不是功能清单更长，而是**它已经被大量项目验证过**：结构化病历、病程模板、术语联动、打印排版这些"医疗特有的硬骨头"，厂商已经替你啃完，还配了文档与技术支持体系。

适合的团队画像很清楚：

- **正式医院落地项目**——排期紧、验收严、容错低，要的是"别出事"；
- **没有长期养编辑器内核团队的计划**——把内核交给厂商维护；
- 预算里**本来就有一笔采购 / 年费**，且能接受供应商绑定。

购买前值得问清的三个问题：

1. **数据主权**：文档以什么格式存储？能否导出、迁移？换供应商时数据带得走吗？（通用商业套件多以私有或文档格式存储，**迁移成本要提前评估**）
2. **扩展边界**：能不能插自定义控件、自定义质控规则？做二次开发时厂商是否提供 SDK / 接口，改造成本由谁承担？
3. **计费口径**：按坐席、按医院、按项目还是按年？后续升级、加模块怎么算？

**它的代价**：不便宜，且**能力上限跟着厂商走**——你提的特殊需求，要排队进别人的 Roadmap。

## 三、路线二：开源内核——买的是"起点"

"开源"不等于"免费"——免费的是**起点**，不是**结果**。

开源内核（如 thinkeditor、SDE，以及一批演示级 canvas 方案）的价值在于：基础编辑能力已经跑通，你不必从零写一个富文本内核。对预算有限又有研发能力的团队，这能省掉最痛的那段"从 0 到 60 分"。

但它对团队有隐性门槛：

- **必须有能读懂、并能修改内核的人**。开源内核一旦出问题，没有厂商兜底，Issue 区不会替你加班；
- **要看清维护强度**。一个仓库最后提交在两年前、Issue 无人回复，那它本质是"一份可参考的代码"，而不是"一个可持续的依赖"。演示级项目和真正在维护的开源项目差别很大——前者适合学习与二次开发参考，**不建议直接商用上线**；
- **许可协议要提前读**。不同开源协议的传染范围不同（是否要求衍生作品同样开源、能否用于闭源商业产品），这直接影响你能不能合法商用。

**它的代价**：省了买产品的钱，却把"长期维护 + 内核演进"的责任接回了自己团队。

## 四、路线三：自研——买的是"上限"和"可控"

自研是三条路里**门槛最高、也最容易被低估**的一条。

它真正适合的，是**编辑器本身构成核心竞争力**的团队：病历排版规则、结构化数据模型、质控逻辑、与自家 HIS / EMR 的深度耦合——这些如果外购，长期会被卡住；只有自己写，才能按业务长出自己的形状。

但自研不是"让前端同学抽空写个富文本"。它至少意味着一支**持续投入的内核团队**，以及一长串必须自己解决的硬问题：

- **排版层**：行断与分页（换行规则、孤行寡行控制）、页眉页脚、页码、纸张级所见即所得；
- **渲染性能**：长文档虚拟滚动、增量排版、脏区局部重排；
- **编辑内核**：Command 撤销栈、剪贴板多格式、IME 中文组合输入；
- **数据层**：结构化控件、域代码、文档比对与版本回溯、审计留痕。

**它的代价**：时间。一个能扛住真实病历场景的内核，往往**以年为单位**投入，还要接受"前几个月没法交付业务"的空窗期。

## 五、一张决策表：按你的约束选路

把上面的判断收敛成一张表：

| 你的处境 | 更该考虑 | 核心理由 |
|---|---|---|
| 大型三甲正式项目，排期紧、要兜底 | 商业套件 | 确定性优先，花钱买履约 |
| 中小机构自研 EMR，预算有限但有研发 | 开源内核 | 省掉"从 0 到 60 分"，聚焦业务 |
| 编辑器是核心竞争力，且愿长期投入 | 自研 | 上限与可控性买不到 |
| 只想做个 Demo / 内部工具 | 开源内核 / 演示级方案 | 够用就好，别过度投入 |
| 已有 HIS，只想补一块病历编辑 | 商业套件 / 可嵌入的开源内核 | 优先看集成成本，而非重造 |

一行话总结：**排期紧、要兜底 → 买；有研发、要省事 → 用开源；要上限、能养团队 → 自研。**

## 六、选型最容易踩的五个坑

功能表谁都会看，真正决定成败的，往往是那些"没人写在对比表里"的东西：

1. **只看功能清单，不看维护承诺**。功能可以演示，但排期紧的项目真正需要的是"出问题多久能响应"。
2. **把开源当免费的商业套件**。"能改"是优点，也意味着"要自己改"。评估开源前，先算清自己团队的二次开发与长期维护成本。
3. **把自研当"顺手做前端"**。编辑器内核的复杂度常被严重低估，尤其排版与性能两关，往往需要专职投入。
4. **忽略数据迁移与退出成本**。无论选哪条路，都提前问一句："三年后我想换，数据能不能带走、界面能不能重接？"
5. **没有兜底方案**。平台方停止维护、核心开发者离职、厂商变更授权策略——方案里应留一条 Plan B。

## 七、坦诚地说：我们为什么选了第三条路

我们这套 **EMR 电子病历文档编辑引擎**，走的是**自研**这条路：**从零手写、不依赖任何第三方富文本框架**（没有 Quill / ProseMirror / Slate / Tiptap），自研 HTML5 Canvas 内核，前端 React 18 + TypeScript，后端 Spring Boot 3.3 + Java 17，采用 MPL-2.0 开源协议，前后端一体开源。

之所以挑这条"最累"的路，是因为病历排版、结构化录入、质控这些能力，天然要跟医疗业务深度绑定——通用富文本框架"改不动"的部分，恰恰是它的核心价值所在。目前它已经具备：A4 纸张级排版、结构化录入控件（8 类）、动态域代码（8 种）、内置质控规则（6 条，支持自定义扩展）、医疗缩写自动更正（25 条）、三层 Canvas 渲染与增量排版、Command 撤销栈（30+ 种可撤销命令），以及模板管理 / 文档比对 / 版本回溯 / 审计日志 / 权限管控的工程闭环。

**按惯例把现状说清楚**：PDF/Word 导出与多人协同编辑仍在推进中，当前可用导出格式为 JSON / TXT / HTML；多人协同的 Yjs 基础设施已就位，编辑流尚未接入。我们不回避这些边界——一份诚实的 Roadmap，比一份"什么都支持"的功能表更值得信任。

## 写在最后

选病历编辑器，没有标准答案，只有**匹配你约束的答案**：扛得住采购成本、要确定性，就买；有研发能力、要省时间，就用开源；有长期决心、要上限，就自研。
