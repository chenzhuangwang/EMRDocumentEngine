# 1500+ 个测试是怎么攒出来的：医疗软件为什么不能靠人工点

> 医疗软件的 bug 有两种：一种让你崩溃，一种让你签字。第二种更贵。

一份病历里，"中性粒细胞"被从中间劈开，"中性粒"和"细胞"分到了两行。

这个 bug 不会崩溃、不会报错、不会在控制台留一行红字。它只是安静地躺在那里，直到医生把纸打印出来、签上字、归进档案——然后被质控科翻出来。

问题来了：**你打算怎么"点"出它？**

## 一、"人工点一遍"为什么在这个场景失效

"我们发版前会人工点一遍"——这句话在大多数产品里是负责的，在病历编辑器里却不够用。三个原因：

**第一，要点的样本是排列组合。** 同一个分页算法，要覆盖不同页数、不同段落长度、段落刚好跨页、页眉页脚占位、表格跨页……人工点只能覆盖"我想得到的那几种"，而 bug 恰恰长在你没想到的那一种里。

**第二，有些错误只在看不见的地方。** 第 47 页的页脚、深色主题下某个对话框没跟着换色、导出的第 3 页多了一个空行。这类问题**不会主动跳到你眼前**，它需要"逐页逐项比对"，而不是"看一眼"。

**第三，也是最麻烦的：有些错误是沉默的。** 不抛异常、不崩界面，只是结果不对。而医疗软件里，"结果不对"往往比"崩了"更严重——崩了你会立刻知道，错了你可能三个月后才知道。

所以这套引擎的选择是：**把"人工点一遍"能覆盖的部分，尽量变成"机器每次提交都跑一遍"。**

## 二、一次全量运行：151 个文件、1537 个用例

先说清楚数据是怎么来的——**截至 2026-09-22 的一次全量运行**（`vitest run`，单次、非 watch）：

| 指标 | 实测值 |
|---|---|
| 测试文件 | **151 个，全部通过** |
| 用例 | **1537 通过 / 1 跳过（共 1538）** |
| 单次全量耗时 | **30.81 秒** |

三个数字里，我最在意的是**第三个**。

**30 秒意味着"每次改完都可以跑一遍"**。如果全量测试要跑十分钟，它的实际使用频率就会退化成"发版前跑一次"——而发版前跑一次，等于把发现问题的时机从"提交时"推迟到了"上线前"，代价完全不同。

也把不漂亮的细节写在这里：**有 1 个用例是 skipped 状态**，我没有把它算进"通过"里；这次运行在 stderr 里还打出了 React 的告警堆栈——不影响结果，但属于还没清理干净的噪音。**"全绿"不该被美化。**

## 三、那些"必须测、人工测不了"的东西

下面这五类，是这套测试账本里最值钱的部分——因为它们的共同点是：**人工验不了，或者验一次要很久。**

### 3.1 分页：一个要翻一百页才能发现的问题

分页有**独立的测试文件**（含孤行寡行控制）。能这么测，是因为分页被设计成了**纯函数**：喂进去一串构造好的行，断言输出的页边界。

这带来一个很实际的好处：**"一份病历的第三页会不会出现孤行"这种问题，可以在毫秒级验完**，而不是生成一份几十页文档、滚动到第三页、用肉眼判断"这里是不是不太对"。

### 3.2 打印投影：那个 `[页码]` 字面量的回归

上一篇讲打印一致时提到过这条回归：打印稿里**页眉页脚整块消失**，正文的页码域打印成了字面量 `[页码]`。

为什么它需要测试？因为**"点一下打印看看"根本发现不了**。要发现它，你得：打一份多页文档 → 逐页翻到有页码的地方 → 确认页码是数字而不是占位符 → 再确认页眉页脚都在。而更早的那一版问题更隐蔽——**它只在某些页面上出现**。

所以这个文件被留了下来，文件头的注释就是那次回归的墓志铭。**一个 bug 修完之后，最该留下的不是修法，是"它不会再回来"的证明。**

### 3.3 用户输入不可信：一律钳制

打印范围是用户填的。用户可以在数字框里填 `0`、`-3`、`999`，也可能填出 `NaN` 和小数。

这个测试文件的 describe 名字直接写着它的立场——**「用户输入不可信，一律钳制」**。里面有一条用例的注释我特别喜欢：

> `end < start` → 收敛成单页（而不是切片成空数组）
> 切片为空 = 交给打印窗口一张图都没有：什么都不打，也不报错。**必须收敛。**

这就是"沉默的错误"的典型：范围填反了，程序不报错，只是**什么都没打**，而用户以为打完了。

### 3.4 契约不变量：把"文档里的约定"变成"CI 会红的事实"

这个仓库里有一份《AI 编辑契约》，规定了引擎不能违反的架构不变量。但**写在文档里的约定，等于没有约定**——没人会每次提交前重读一遍。

于是有了一个专门的测试：**扫描引擎全部源码，把可静态判定的"必须 / 禁止"固化成断言，任何一条违例直接 FAIL。** 覆盖的项包括：

- 引擎层**禁止使用浏览器全局**（`document` / `window` / `navigator`…）；
- 引擎层**禁止依赖 React**、**禁止依赖 Yjs**；
- 依赖方向：引擎**不得反向依赖** platform / UI；
- 文档模型有**唯一变更咽喉**（节点池的写入只有一处入口）；
- 某些非结构字段**禁止外部直写**；
- 某些配置类型只有**唯一的 canonical 归属**。

文件注释把动机写得很清楚：**"这类不变量此前靠人肉审计 + 注释约定；本测试让回归在 CI 直接暴露。"**

### 3.5 主题门禁：闸门自己漏扫，比没有闸门更危险

最后一个是我认为最"工程"的一条。

给界面做深色主题时，真实的失败模式不是"某个组件没换色"，而是**换了一半**：外层面板跟着主题走了，里面的对话框、输入框还钉死在白灰上——深色模式下一块块刺眼的白洞。文件注释的原话是：**"靠肉眼扫 40 个文件基本发现不了。"**

于是有了一条 CI 硬闸门：扫描 UI 源码，**禁止再出现硬编码的中性色**。而且——扫描范围必须包含 `index.css`，因为某个被大量复用的按钮样式写在 CSS 里，只扫 `.tsx` 的闸门会漏掉这个最高杠杆点。

更妙的是它自己踩过的坑，也被写进了注释：

> 两种看起来该 work 的读法都**静默返回空串**……两种失败都是**静默**的：断言拿到空字符串，一条违例都找不出来，**闸门照样全绿**。
> 这正是下面那条"扫描覆盖"用例存在的理由——**闸门自己漏扫比没有闸门更危险。**

一句话：**测试不仅要测产品，还要测"测试自己有没有真的在测"。**

## 四、测试也有它的边界

写到这儿，得把没做到的一并说清，否则这篇就成了自我表扬：

- **端到端（E2E）测试还没做。** 项目里有 Playwright 依赖、也有 `test:e2e` 脚本，但仓库里**没有 Playwright 配置、也没有一条 E2E 用例**——契约里登记为"规划中"。这意味着**"人工点"并没有被完全替代**：真实浏览器里的粘贴、中文输入法的组合输入、跨浏览器的打印表现，目前仍然要靠人。
- **1537 个用例不等于"没有 bug"。** 它只说明**已经踩过的坑被钉住了**。没踩过的坑，照样会漏。
- **测试数量不是质量分。** 堆用例很容易，难的是"每条用例都在守一个真实会发生的错误"。判断标准很简单：**删掉这条用例，有没有可能让一个真实 bug 溜过去？**
- **跑得动才有意义。** 30 秒能跑完，才可能每次都跑；测试如果慢到没人愿意等，它就会从"防线"退化成"仪式"。

## 五、回到场景

医疗软件的 bug 有两种：**一种让你崩溃，一种让你签字。**

前者会有人报障、会有人骂、会连夜修；后者安安静静地进入档案，可能几个月后才被质控科翻出来——那时候，代价已经不是"改一行代码"了。

测试账本的全部意义，就是把"翻一百页才发现"提前到"提交前 30 秒"。

**一份病历不该是医生的负担，也不该是"没人测过就上线"的赌注。**
