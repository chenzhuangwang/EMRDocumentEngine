## 0. 契约总则

### 0.1 本契约解决什么问题

本项目已完成一年的独立开发，具备完整的编辑器内核与工程闭环，但**传播基数极低（9 Star）**。制约因素不是产品力，而是：

1. **曝光缺失**：除 3 篇公众号文章外，几乎没有分渠道、分受众的系统性传播；
2. **口径不一**：已有文章中部分数据与代码事实不符（详见 [1.4](#14-事实合规红线口径统一表)），存在信任风险；
3. **转化漏斗断裂**：缺少 "内容 → 仓库 → Star → Issue/PR" 的可追踪链路与运营动作。

本契约将上述问题转化为乙方可执行、可验收的职责。

### 0.2 约束优先级（冲突时的裁决顺序）

```
1. 事实真实性      — 任何宣称必须有代码/仓库事实支撑
2. 合规与平台规则   — 不刷量、不诱导、不违规互刷
3. 目标达成        — Star 增长
4. 执行效率        — 产出速度与复用度
```

**任何情况下不得为达成指标而牺牲第 1、2 条。**

#### 5.2.1 掘金（核心引擎）

- **定位**：技术深度第一阵地，主打受众 B，兼顾 A；

- **发布要求**：必须含可运行代码片段 / 架构图 / 真实截图；文末统一 CTA（见附录 B）；
- **互动**：发布后 2 小时内回复全部评论（甲方答疑为主，乙方整理）。

#### 5.2.2 微信公众号（垂类沉淀）

- **定位**：面向 A / C 的场景与价值叙事，延续已有 3 篇的调性（"让医生少敲键盘"）；

- **优势**：可沉淀私域、可被行业群转发；
- **禁忌**：不写技术细节堆砌（技术细节放掘金）。

#### 5.2.3 知乎（决策链渗透）

- **打法**：**回答优先于发文**。搜索"电子病历 编辑器 开源""病历编辑器 选型""HIS 电子病历 自研"等问题，输出专业回答；

#### 5.2.4 Gitee 主阵地运营

1. **README 首屏优化**（需授权）：首屏 5 秒内讲清"是什么 + 差异点 + 一键体验 + 截图"，已有 badge 与预览图基础良好；

#### 5.2.5 V2EX / 社区（高风险高回报）
