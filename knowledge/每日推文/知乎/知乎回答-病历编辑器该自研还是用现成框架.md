## 回答正文

**先说结论：这个问题不该问"哪个更好"，该问"你的约束有几条"。**

我在做电子病历编辑器的选型时，ProseMirror、Slate、Tiptap 都试过，最后选择了从零手写内核。但这不是一个"自研更牛"的故事——如果你做的是博客、笔记、IM、评论，或者病历编辑器只是要"能打字、能加粗"，那直接用现成框架，自研只会让你死在没必要的复杂度上。

真正决定要不要自研的，是下面三个约束是否**同时**成立。

### 一、什么情况下应该用现成框架 / 魔改

- **内容是流式的**：从上往下排，换行分页交给浏览器。这正是 ProseMirror / Slate 这类框架的核心假设，硬要在它上面做纸张级分页，成本比自研还高；
- **需要成熟的协同生态**：现成框架有现成的协作方案，自研内核再叠自研协同是双重风险；
- **团队没有长期投入的打算**：编辑器内核是需要几年打磨的东西，做一半比不做更糟；
- **你只是想在 contenteditable 上贴一个工具栏**：那本来就不需要"内核"。

### 二、什么情况下通用框架会真的卡住你

如果下面三条**同时**成立，通用富文本框架会从"省事"变成"负债"：

**1）纸张级分页。** 病历的分页不是视觉问题，是正确性问题——"预览的第 3 页"必须等于"打印出来的第 3 页"，还要处理跨页表格表头重复、孤行寡行、页眉页脚页码域。流式模型下这些要么做不到，要么各端行为不一致。

**2）结构化字段不是"一段文本"。** 病历里的"体温 36.8℃""用药剂量"不是字符串，是带元数据的原子节点：字段名、单位、数据类型、必填性、校验规则，不能被你逐字拆到两行里去，还要参与质控和统计。通用框架里它顶多是"一段带样式的文本"。

**3）引擎不能被浏览器绑死。** 如果你希望内核能嵌进 React / Vue / Electron，甚至跑在 Web Worker 里做无头排版，那渲染就不能落在 DOM 上——而这类框架的渲染终点恰恰是 DOM。

### 三、自研的真实代价（必须讲清楚）

- **时间**：文档模型、排版引擎、渲染管线到外壳，一年；
- **边界情况**：行断、分页、光标寻址、IME、剪贴板，每个都是无底洞；
- **生态为零**：现成框架有庞大的插件生态，自研是 0，所有能力都得自己写；
- **人才**："会 ProseMirror"的简历一大把，"写过 Canvas 富文本内核"的几乎没有。

### 四、自研之后换来的是什么（摘要）

我们把"排版"从"渲染"里拆了出来，做成一条单向管道（文档模型 → 排版引擎 → 渲染），分页于是变成纯函数，可预测、可缓存、可增量；变更全部走 Command 并只有一个撤销栈 owner，500ms 内连续输入自动合并成一次撤销；中文行断实现了避头尾规则，同时把结构化字段当原子元素处理。

完整的技术取舍与代码，我写了一篇长文放在掘金，这里不重复展开：`（掘金长文链接 · 发布后回填）`

### 五、诚实披露

这个项目当前**可用导出格式为 JSON / TXT / HTML，PDF / Word 导出与多人协同仍在推进中**。把未完成的能力说清楚，比把它包装成"已支持"更重要——选型的人最怕的就是这种落差。
